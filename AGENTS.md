# Разработка TomeNET SV

Правило пользователя от 2026-09-22: при разработке SV минимизировать изменения
существующего клиента и общих файлов. Реализацию и адаптацию по возможности
размещать в SV. Дублирование реализации допустимо, если оно позволяет сохранить
изоляцию и не подключать большой набор зависимостей. Общий код выделять, когда
это нужно для текущей задачи, а не только ради устранения дублирования.

При переносе сохранять протокольную и игровую семантику behavior baseline.
Тесты должны вызывать production-путь SV; локальная SV-реализация допустима,
отдельная реализация поведения только для тестов — нет.

Обнаруженные возможности улучшить legacy, общие модули или организацию SV
записывать в [список улучшений](docs/sv-improvements.md), отдельно от реализации
текущей возможности. Для каждой записи указывать проблему, затронутый код,
предложение, статус и необходимые проверки. Запись сама по себе не включает
улучшение в текущую задачу. Намеренное дублирование ради изоляции не является
само по себе дефектом или обязательством последующего объединения.

Это правило имеет приоритет над прежними формулировками проектных документов,
требующими общей реализации SV и legacy. Архитектура SV описана в
[docs/sv-architecture.md](docs/sv-architecture.md).

## Agent skills

### Issue tracker

При создании, triage и review задач используйте локальный Markdown: Wayfinder в `.scratch/`, SV implementation tickets в `docs/tasks/`. Правила путей и статусов — в [docs/agents/issue-tracker.md](docs/agents/issue-tracker.md).

### Triage labels

При triage используйте пять стандартных ролей и отдельное поле `Labels:`. Соответствие ролей — в [docs/agents/triage-labels.md](docs/agents/triage-labels.md).

### Domain docs

Перед работой с доменными терминами или архитектурой читайте корневой `CONTEXT.md` и относящиеся к задаче ADR. Правила single-context layout — в [docs/agents/domain.md](docs/agents/domain.md).
