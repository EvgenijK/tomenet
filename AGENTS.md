# Разработка TomeNET SV

Правило пользователя от 2026-09-22: при разработке SV минимизировать изменения
существующего клиента и общих файлов. Реализацию и адаптацию по возможности
размещать в SV. Дублирование реализации допустимо, если оно позволяет сохранить
изоляцию и не подключать большой набор зависимостей. Общий код выделять, когда
это нужно для текущей задачи, а не только ради устранения дублирования.

При переносе сохранять протокольную и игровую семантику behavior baseline.
Тесты должны вызывать production-путь SV; локальная SV-реализация допустима,
отдельная реализация поведения только для тестов — нет.

Обнаруженные возможности улучшить legacy, общие модули или организацию SV
записывать в [список улучшений](docs/sv-improvements.md), отдельно от реализации
текущей возможности. Для каждой записи указывать проблему, затронутый код,
предложение, статус и необходимые проверки. Запись сама по себе не включает
улучшение в текущую задачу. Намеренное дублирование ради изоляции не является
само по себе дефектом или обязательством последующего объединения.

Это правило имеет приоритет над прежними формулировками проектных документов,
требующими общей реализации SV и legacy. Архитектура SV описана в
[docs/sv-architecture.md](docs/sv-architecture.md).

## Agent skills

### Процесс реализации

Правило пользователя от 2026-10-27: прежний процесс реализации Sandcastle
удалён; новый строится с нуля. Для достижения цели задачи вносите минимальные
правки и добавляйте только самый необходимый минимум тестов самого core,
вызывающих production-путь. Расширение набора проверок согласовывайте с
пользователем заранее. Эти ограничения имеют приоритет над прежними
требованиями процесса. Текущее состояние — в [docs/sandcastle.md](docs/sandcastle.md).

### Платформы сборки и проверки

Правило пользователя от 2026-10-28: для задач всех этапов SV текущая
обязательная платформа — Linux. Windows/MinGW/Wine сборки и проверки временно
отложены до отдельного решения пользователя и не блокируют текущую приёмку.
При выборе проверок и оценке статуса применяйте
[правило платформ](docs/agents/platform-validation.md), включая Windows-only
задачи, старые cross-platform gates и историческое evidence.

### Issue tracker

При создании, triage и review задач используйте локальный Markdown: Wayfinder в `.scratch/`, SV implementation tickets в `docs/tasks/`. Правила путей и статусов — в [docs/agents/issue-tracker.md](docs/agents/issue-tracker.md).

### Triage labels

При triage используйте пять стандартных ролей и отдельное поле `Labels:`. Соответствие ролей — в [docs/agents/triage-labels.md](docs/agents/triage-labels.md).

### Domain docs

Перед работой с доменными терминами или архитектурой читайте корневой `CONTEXT.md` и относящиеся к задаче ADR. Правила single-context layout — в [docs/agents/domain.md](docs/agents/domain.md).

## graphify

Graphify установлен только в этом проекте: CLI — `.graphify-venv/bin/graphify`,
Python — `.graphify-venv/bin/python`. При вызове `$graphify` (или `/graphify`)
читайте [.agents/skills/graphify/SKILL.md](.agents/skills/graphify/SKILL.md).
Пакет и дополнительные зависимости устанавливайте в это локальное окружение.

Если `graphify-out/graph.json` существует, перед поиском по исходникам для
вопроса о кодовой базе выполняйте `.graphify-venv/bin/graphify query "<question>"`.
Передавайте это правило подагентам, исследующим код. Для связей и отдельных
понятий используйте подкоманды `path` и `explain`; исходники проверяйте для
уточнения ответа. Если граф отсутствует, устарел или не даёт нужного контекста,
используйте обычный поиск и чтение файлов.

После изменения кода обновляйте существующий граф командой
`.graphify-venv/bin/graphify update .`. Генерация графа впервые запускается
отдельно через `$graphify .`; результаты в `graphify-out/` игнорируются Git.
