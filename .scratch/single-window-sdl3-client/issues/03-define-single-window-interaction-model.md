# Define the single-window interaction model

Type: prototype
Status: resolved
Assignee: codex
Blocked by: 01, 02

## Question

Как одно системное окно организует все возможности behavior baseline через постоянные области, вкладки, primary/context/dialog/target/system overlays, focus return и responsive layout, не воспроизводя legacy-терминалы и сохраняя подтверждённый UX prototype?

### Проверка отмены targeting по запросу пользователя

`cmd_target` (`src/client/c-cmd.c:2040`) возвращает FALSE при Esc/q и при нераспознанном как направление вводе, очищая top line, без affirmative `Send_target(5)`. `get_dir` (`src/client/c-util.c:3672`) при `*` вызывает этот цикл; после отказа dir остаётся 0, функция возвращает FALSE, без повторного direction prompt. Например `cmd_aim_wand` (`src/client/c-cmd.c:1858`), направленная activation, mimic power, runecraft и breath прекращают действие без отправки action packet. Самостоятельный `*` завершает только команду выбора цели. `cmd_target_friendly` не имеет такого cursor loop: посылает init и возвращает TRUE. Наличие/сброс ранее сохранённой цели определяется отдельно серверной семантикой; FALSE не следует трактовать как обязательную очистку current target.

В демо ошибочно был показан неподтверждённый «штатный возврат к предыдущему шагу» после отмены цели. Этот сценарий и кнопка retry удалены по проверенным фактам; текущий прототип демонстрирует полную отмену get_dir → cmd_target. Условная формулировка Q2 о baseline retry не доказывает наличие такого пути и не разрешает его добавлять. Отмена нового UI-диалога без штатного аналога обсуждается отдельно в Q7 и не заменяет targeting semantics.

## Answer

### Организация surfaces

Единственное SDL_Window содержит постоянную игровую основу, одну основную рабочую surface (`primary`) и дочерние surfaces текущего взаимодействия (`context`, `dialog`, `target`). Это семантические surfaces, не physical/virtual Terms. Новая primary заменяет предыдущую; закрытый раздел автоматически не восстанавливается. HUD и ленты остаются видимыми при обычной достаточно широкой компоновке, не образуя дополнительных независимых рабочих разделов. Открытый рабочий раздел блокирует случайный gameplay input, но не останавливает online game; штатные доступность команд и routing определяются baseline input contexts.

- Inventory/Equipment/Character/Skills/Abilities/Messages/Mini-map используют подтверждённые UX entry points и один primary. Messages открывается разделом, как Inventory/Abilities, заменяя текущий primary; независимая раскрываемая «дополнительная лента» для малой ширины не вводится.
- Social/Knowledge/Help/Settings/macros/tools — primary с внутренней навигацией «категории → страница → дочерние диалоги». Вкладки группируют содержимое, не добавляют game semantics или память между завершёнными interactions.
- Магазин контекстно открывает primary, заменяя предыдущий раздел; товары либо Go/казино находятся внутри него. Количество, текст и подтверждения — дочерние surfaces со штатными responses, cancel/abort и lifecycle. UI-навигация не разрешает произвольно отменять активный store/request flow.
- Серверные документы показываются внутри соответствующего раздела, произвольный document — в общем просмотрщике. Исходные строки/цвета и неизвестное content остаются доступными; дополнительные semantic projections не заменяют lossless representation. Специальное магазинное содержимое — drawing/animation область внутри магазина, не текстовый документ и не terminal fallback. Local Guide остаётся отдельным источником.
- Подключение, выбор/создание персонажа, смерть и повторный вход — последовательные состояния того же SDL_Window со штатным порядком.

### Ввод и завершение

Targeting временно скрывает перекрывающие карту surfaces, сохраняя состояние незавершённого взаимодействия, и передаёт ввод карте в target context; критический HUD и ленты остаются видимыми. После законченной игровой команды цепочка закрывается и управление возвращается карте, кроме предусмотренного baseline продолжения в разделе. Состояние раздела после этого не запоминается для следующего открытия, если оригинальный клиент его не сохраняет. Game state, например current target, следует собственному baseline lifecycle.

Отмена определяется конкретным baseline flow. Проверенный путь `get_dir → cmd_target` при Esc/q отменяет действие целиком, без возврата к списку или повторного direction prompt и без отправки финального action packet; самостоятельный `*` завершает только выбор цели. Неподтверждённый targeting retry из демо удалён. Чат открывается ровно в предусмотренных оригинальным клиентом contexts; общий UI-флаг не расширяет/сужает точки входа. Полная macro/binding/retry матрица уточняется в [Preserve input and macro semantics](04-preserve-input-and-macro-semantics.md).

В UI-навигации без штатного аналога Esc закрывает верхнюю дочернюю surface и возвращает focus действующему opener; при его недоступности — доступному элементу действующего родителя. Это не восстанавливает завершённый flow. Штатный Esc имеет приоритет над этим UI-правилом.

Системная surface получает приоритет ввода, показывает причину и даёт только штатные варианты выхода/повторного входа. Завершение сессии закрывает старые interactions; relogin не восстанавливает старые диалоги/команды и не отправляет их повторно. EOF, PKT_QUIT и conditional PKT_RELOGIN имеют разные baseline outcomes; универсального reconnect/resume не добавляется. Обычный event не получает семантику завершения сессии лишь из-за визуального системного слоя. Evidence проверки исходного кода приведено выше.

### Адаптация и граница решения

Положение этой резолюции и исторического Q5 о сворачивании дополнительных панелей заменено последующим решением пользователя в [Specify surface layouts and responsive rules — Automatic layout changes rejected / Panel widths confirmed](21-specify-surface-layouts-and-responsive-rules.md#automatic-layout-changes-rejected-by-user). Геометрия и fitting определяются там. Resize не отменяет команду и не сбрасывает input. «Места мало» в старом демо — имитация resize, не отдельный пользовательский режим клиента и не актуальное evidence окончательной компоновки. Доступ к сообщениям остаётся через Messages primary.

Прототип и пользовательский verdict зафиксированы выше. Конкретные per-capability layouts, density/size thresholds, collapsed controls и размещение длинного/special content ещё не выбраны: fog переведён в [Specify surface layouts and responsive rules](21-specify-surface-layouts-and-responsive-rules.md), который блокирует acceptance. Rendering parity, command/macro semantics, settings persistence и latency budgets остаются в соответствующих существующих тикетах. Runtime client не реализовывался; код демо в него не переносится на planning-этапе.
