# Set the compatible protocol-extension policy

Type: grilling
Status: resolved
Assignee: codex
Blocked by: 01, 11

## Question

При каких строгих условиях допустимо предлагать необязательные серверные расширения: как проверяются отсутствие влияния на старые клиенты, negotiation/fallback нового клиента, сохранение server authority и корректное состояние UI при недоступности расширенных данных; и какая policy применяется к существующим асимметричным или dormant endpoints вроде `PKT_LEAVE` и `PKT_PRAY`, которые нельзя безопасно реактивировать односторонне?

## Answer

Согласовано с пользователем 2026-09-13: приняты рекомендации по всем трём вопросам после уточнения незавершённых packet-путей.

### Условия допуска

Необязательное расширение можно предлагать только для конкретного пользовательского outcome, с доказательством, что нужные данные нельзя корректно получить через текущий протокол. Полнота behavior baseline достигается без расширений; расширение не становится prerequisite завершённого клиента.

### Обязательный контракт совместимости

- Поддержка явно согласуется до отправки новых packets. Отсутствие или отказ поддержки сохраняет корректное базовое поведение нового клиента.
- Старые клиенты продолжают работать без изменений. Для каждого предложения требуется проверяемое evidence неизменного поведения, а не предположение по наличию packet ID.
- Server authority сохраняется: новые данные не дают UI права самостоятельно определять игровой результат или обходить серверные проверки.
- UI различает недоступные данные и нулевое значение, сохраняет базовые actions и сбрасывает расширенные данные при смене сессии.
- Контракт каждого предложения описывает negotiation, fallback, lifecycle данных и проверки этих условий. Конкретный механизм negotiation выбирается только для конкретного предложения; эта policy не вводит новые packets.

### Незавершённые packet-пути

Наличие packet ID, функции отправки или служебного упоминания не доказывает работающий полный путь.

- `PKT_LEAVE`: сервер имеет `Send_leave`, но source-wide audit не обнаружил её вызовов; на клиенте нет receive binding. Одностороннее включение отправки заставит старый клиент обработать пакет как неизвестный, запросить redraw и очистить receive buffer.
- `PKT_PRAY`: клиент имеет `Send_pray`, но её вызовов не найдено; серверные упоминания в energy checks не являются receive binding. При отправке пакет попадает в `Receive_undefined`, который отбрасывает содержимое receive buffer.

Это характеристики конкретных packet-путей, не утверждение о неработоспособности выхода из игры или молитв как capabilities. Evidence: [packet-state audit](../../../docs/research/single-window-packet-state.md), `Send_leave` в `src/server/nserver.c:4796`, `Send_pray` в `src/client/nclient.c:7869`, `Receive_undefined` в `src/server/nserver.c:6411`.

Односторонняя реактивация запрещена. Использование требует отдельно согласованного контракта обеих сторон и evidence совместимости; до этого новый UI не использует эти packet-пути. Удаление или реализация таких путей не входят в эту planning-карту.

### Последствия для карты

[Design parity evidence and acceptance](09-design-parity-evidence-and-acceptance.md) должен учитывать проверки базового поведения без расширений, negotiation/fallback, отсутствия влияния на старые клиенты, server authority и lifecycle недоступных данных. Его существующая зависимость от этого решения достаточна; новых tickets или уточнившихся участков fog это решение не создаёт.
