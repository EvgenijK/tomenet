# SV-ARCH-001 — Привести текущий shell и HP-срез к согласованной архитектуре

Статус: выполнена. Дата: 2026-09-21.
Тип: корректировка текущих изменений Stage A, tickets 01–02.

## Цель

Привести уже начатый `tomenet-sv` к [согласованной архитектуре](../sv-architecture.md)
до расширения набора возможностей. На существующем synthetic shell и HP-срезе
должны работать разделение протокола и модели, последовательная обработка с бюджетом,
предупреждения через отдельный модуль, версии UI, lifecycle сессии и смысловые ошибки.
Новая возможность не должна требовать добавления игровой ветки в центральный `app.c`.

Обязательные основания: [словарь](../../CONTEXT.md) и ADR
[0001](../adr/0001-separate-session-interactions-and-ui.md),
[0002](../adr/0002-main-thread-state-ownership.md),
[0003](../adr/0003-explicit-module-connections.md),
[0004](../adr/0004-revision-based-ui-views.md),
[0005](../adr/0005-session-scoped-work.md),
[0006](../adr/0006-errors-and-overload.md).

## Исходное состояние

Задача составлена по рабочему дереву, включающему незакоммиченные и untracked файлы.
Перед реализацией сверить актуальное состояние; существующие изменения сохранять.

| Место | Наблюдение | Требуемая корректировка |
|---|---|---|
| [session.c](../../src/client/sv/session.c) | `SvSession` содержит player, wire version, sockbuf, dispatch, revision и failed | Развести protocol adapter, модель и lifecycle через содержательные интерфейсы |
| `sv_session_feed()` | Разбирает весь доступный буфер; результат только `0/-1` | Отделить поступление байтов от ограниченного продвижения обработки, различать ожидание, прогресс и ошибки |
| [main.c](../../src/client/sv/main.c) | Сборка, rendering и вызовы сценариев находятся рядом; общий выход освобождает всё приложение | Выделить сборку/lifecycle и UI по ответственности; ошибка сессии не должна автоматически завершать приложение |
| `frame()` и [status.c](../../src/client/sv/status.c) | HP читается и форматируется каждый кадр, revision не используется UI | Обновлять производное представление по версии и зависимостям отображения |
| [synthetic.c](../../src/temporary/sv/synthetic.c) | Готовые байты применяются в bootstrap до главного цикла | Пропускать synthetic-вход через тот же путь обработки приложения, который проверяется бюджетом и lifecycle |
| [sv-hp.md](../sv-hp.md) | Native-путь пока не выдаёт предупреждения; реальные audio/preferences отсутствуют | Реализовать проверяемые правила HP-предупреждений и передачу результатов без добавления полноценной аудиоподсистемы |

Уже полезные свойства сохранить: opaque session, единственное хранилище HP,
копия малого semantic snapshot, один поток-владелец, общий legacy/SV HP decoder,
production `Packet_scanf`, изолированная сборка и разделение temporary/test sources.

## Объём работ

### 1. Разделить текущие ответственности

- Protocol adapter владеет версией, wire buffers, partial decode, dispatch и
  baseline-восстановлением. Полное декодирование даёт типизированное смысловое изменение.
- Модель применяет изменения и предоставляет HP/status без доступа потребителей к
  `player_type`, socket buffers, wire versions, legacy globals и `Term`.
- Application собирает модули, ведёт lifecycle и порядок обработки; UI владеет
  представлением. Допустим небольшой protocol dispatch по типам пакетов, но не
  центральный switch приложения по всем игровым ситуациям.
- Не дублировать изменяемый HP и не переписывать проверенную семантику
  [hp-update.h](../../src/client/hp-update.h). Если helper требует структур legacy,
  скрыть зависимость внутри реализации, не выносить её в UI-facing headers.
- Конкретные имена файлов и сигнатуры выбирает исполнитель. Не создавать пустые
  модули для будущих инвентаря, карты, чата или input router.

### 2. Ввести управляемое продвижение обработки

- Разделить добавление доступных байтов и обработку входов; один полный decoded
  update применяется целиком вместе с вычислением и передачей его реакций.
- Незавершённый пакет не изменяет модель, версии и результаты. Не повторять уже
  применённое изменение после возобновления обработки.
- Главный цикл ограничивает число входов или время работы и возвращает управление
  UI между целыми входами. Остаток сохраняется в порядке поступления.
- Внешние исполнители не изменяют модель рекурсивно; завершения отложенной работы
  возвращаются отдельными входами. Не вводить универсальную event bus ради этого.
- Лимиты и состояние backlog должны быть доступны для проверки. Неблокирующее
  принятие выходных байтов не означает ожидания физического завершения отправки.

### 3. Отделить HP-предупреждения

- Модель предоставляет смысловое изменение с необходимыми предыдущими и новыми
  значениями; отдельный модуль предупреждений получает его, настройки и явный
  смысловой контекст внимания. Он возвращает адресные результаты для исполнителей.
- Сохранить условия legacy `Receive_hp`, включая low-HP предупреждение на каждый
  подходящий пакет, drain и отдельную off-panel реакцию. Не заменять их только
  пересечением порога или проверкой итогового HP в конце кадра.
- Производственная логика предупреждений проверяется без SDL audio и настоящего
  окна. Temporary/test sink фиксирует результаты и порядок доставки; в обычном
  synthetic shell параметры задаются явно, без чтения личных настроек игрока.
- В рамках среза контекст внимания задаётся явно в сценариях. Не объявлять произвольный
  focus/visibility эквивалентом legacy `screen_icky`: привязка к будущим UX-surfaces
  остаётся отдельной работой и отмечается в документации.

### 4. Использовать revision в текущем UI

- HP/status остаётся маленьким snapshot по значению. UI кэширует подготовленное
  представление и не форматирует неизменившийся HP каждый кадр.
- Учитывать применимые зависимости кэша: поколение сессии, revision данных,
  шрифт, масштаб и геометрию. Новая сессия с тем же числом revision не должна
  получить старое представление. Инвалидировать только зависящие от изменения данные.
- Уточнить контракт revision: версия состояния/инвалидации не является механизмом
  доставки разовых реакций. Повторный подходящий HP-пакет не теряет предупреждение,
  даже если видимые значения не изменились.
- Не хранить заимствованные указатели на модель между кадрами. Не вводить систему
  частичных обновлений карты или сложный граф кэшей до появления этих данных и измерений.

### 5. Реализовать lifecycle и смысловые ошибки на существующем срезе

- Владелец lifecycle создаёт поколение сессии и закрывает его; входы/результаты
  старого поколения после закрытия не применяются и не создают исходящих команд.
- Освобождение ресурсов обязательно и при отбрасывании результата. Контракт
  проверить подстановкой запоздавшего результата; worker pool для этого не нужен.
- Различать частичный ввод, восстановимую protocol-ситуацию, ошибку дополнительного
  исполнителя и невозможность продолжать сессию. Небольшая ёмкость буфера вызывающей
  стороны не должна неразличимо выглядеть как отсутствие выходных данных.
- Сохранить baseline unknown-packet recovery, включая предусмотренное отбрасывание
  оставшейся входной порции; не смешивать его с запрещённой молчаливой потерей данных
  при перегрузке. Сохранить версии HP-пакетов и все существующие marker semantics.
- Буферы ограничены. Сначала удерживать/ограничивать дальнейший приём там, где это
  возможно; при невозможности сохранить обязательные данные явно завершать сессию.
- Ошибка сессии оставляет synthetic-приложение отзывчивым с понятной причиной.
  Ошибка звукового sink не закрывает сессию. Отдельно сохраняются нормальный выход
  пользователя и ненулевой результат проваленного автоматического сценария.

### 6. Обновить сборку и документацию

- Обновить [makefile.sv](../../src/makefile.sv) с сохранением независимых build outputs
  и явного разделения production, shared core, temporary и scenario sources.
- Сценарии и проверки не переносятся в production-модули; временные адаптеры остаются
  в `src/temporary/sv`. Реальный путь сборки и исполнения должен быть проверен,
  а не заменён параллельной тестовой реализацией архитектуры.
- Обновить [sv-shell.md](../sv-shell.md) и [sv-hp.md): интерфейсы и lifecycle,
  запуск проверок, достигнутые результаты и оставшиеся ограничения.

## Критерии приёмки

- [x] UI и предупреждения не читают wire buffers, legacy globals или `Term`;
  модель не зависит от SDL, audio и конкретных widgets.
- [x] Существует один реальный путь synthetic bytes → protocol → model → alerts/results
  → UI/исполнители; игровые правила не перенесены в application dispatcher.
- [x] Все прежние HP fixtures, границы частичного ввода, маркеры и версии сохранены.
- [x] Серия HP `50 → 10 → 50` при максимуме 100 до одного кадра оставляет итоговые 50
  и выдаёт положенные промежуточные реакции. Повторные low-HP пакеты, drain и настройки
  проверяются независимо от частоты рисования.
- [x] При малом бюджете серия пакетов продолжается несколькими проходами без потери,
  перестановки и повторного применения; UI получает управление до исчерпания backlog.
- [x] Неизменившиеся данные не вызывают повторную подготовку HP-представления;
  изменение данных, зависимостей кэша и поколения сессии обновляет нужное представление.
- [x] Закрытая сессия не принимает команды; запоздавший результат не влияет на новую.
- [x] Partial input ожидается, unknown recovery сохраняется, overflow сообщается;
  отказ дополнительного исполнителя не закрывает сессию, критичный отказ закрывает
  её без автоматического завершения приложения.
- [x] Логика протокола/модели/предупреждений/lifecycle проверяется без настоящего
  окна, сервера и звука; native smoke отдельно подтверждает отображение и отзывчивость.
- [x] Legacy regression и доступная платформенная матрица не ухудшены;
  непроверенные платформы явно перечислены, сборка не выдаётся за runtime-проверку.

## Верификация

Добавить проверки перечисленных контрактов через реальные интерфейсы модулей.
Они должны ловить потерю промежуточных реакций, двойное применение пакета, голодание UI,
устаревший результат и неверную инвалидацию, а не только повторять внутреннее устройство.
Для проверки бюджета предпочесть детерминированный лимит входов; временные лимиты
и производительность отдельно измерять, без зависящих от скорости машины assertions.

Сохранить существующие проверки либо обновить их вызовы с документированием замены:

```sh
make -C src -f makefile.sv tomenet-sv
python3 tests/sv_hp_checks.py --legacy-only
python3 tests/sv_hp_checks.py --backend software
python3 tests/sv_hp_checks.py --backend opengl
python3 tests/sv_shell_smoke.py --backend software
python3 tests/sv_shell_smoke.py --backend opengl
make -C src -f makefile.sdl3 tomenet
```

Для MinGW/Wine использовать задокументированные SDK и окружение из sv-shell/sv-hp,
если они доступны; не считать Wine подтверждением работы на настоящей Windows.
Число старых проверок не сокращать ради сохранения прежнего summary; новые сценарии
и ожидаемые summaries обновлять согласованно. Проверки проводить на изолированных профилях.

## Вне объёма

Live login/transport, полноценные chat/inventory/map/input flows, настоящая аудиосистема,
загрузка личных preferences, worker pool, ECS, event sourcing и глобальная шина.
Для будущих взаимодействий сейчас фиксируется совместимый контракт, а не создаётся
пустой framework. Исторические `main-modern.c` и agent pack не заменяют нормативный
SV-дизайн. Несвязанные изменения рабочего дерева, включая server map export,
пользовательские файлы, логи и артефакты браузера, в эту задачу не входят.

## Результат

Реализация корректировки, проверки и обновлённые инструкции воспроизведения.
В итоговом отчёте сопоставить изменения с ADR, перечислить выполненные проверки
и реальные ограничения. Завершение этой задачи подтверждает архитектуру текущего
shell/HP-среза, а не готовность всего нового клиента или всего Stage A.

## Выполнение — 2026-09-21

Реализованы `SvApp`, `SvProtocol`, модель сессии, отдельные HP-предупреждения,
смысловые результаты ошибок и кэш HP-представления. Synthetic bootstrap только
ставит байты в очередь; главный цикл обрабатывает до 16 полных входов за проход.
Поколение сессии проверяется для входов, исходящих данных и owned completions;
при BACKPRESSURE/BUSY владелец сохраняет результат для повторной передачи.

Полная Linux-матрица выполнена один раз; после review-исправлений повторены
headless-проверки, SV build и оба затронутых native software-сценария.
MinGW-компилятор доступен, но необходимые cross SDL3/SDL_ttf/FreeType SDK и прежнее

Таблицы предыдущей проверки от 2026-09-20 остаются историческим результатом.

Контекст внимания в synthetic-сценариях задаётся явно; соответствие будущим
UX-surfaces, реальные audio/preferences и live network остаются вне объёма.
Кэш экономит подготовку HP-текста/компоновки; rasterization по-прежнему выполняет
существующий font adapter. Бюджет 16 — исходный лимит числа входов, не подтверждённая
гарантия времени кадра. Новые worker threads и framework для будущих features не добавлены.
