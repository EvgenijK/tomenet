# SV-ARCH-003 — Сгруппировать исходники SV по модулям

**Статус:** implemented; Linux checks passed, MinGW/Wine unverified (missing dependencies).
**Дата:** 2026-09-22.
**Тип:** организация существующей реализации SV.
**Зависимости:** реализация Stage A 01–06 присутствует; отсутствие MinGW
зависимостей не блокирует перенос, но ограничивает платформенную проверку.
**Основание:** [правило изоляции SV](../../AGENTS.md),
[архитектура SV](../sv-architecture.md),
[SV-IMP-006](../sv-improvements.md#sv-imp-006--группировка-исходников-sv-по-ответственности).

## Проблема и результат

Плоский каталог `src/client/sv` смешивает сборку приложения, модель сессии,
протокол, ввод, отрисовку и диагностику. Требуется сгруппировать существующие
файлы по ответственности, чтобы владелец поведения был виден из пути.

Это перенос файлов с адаптацией includes, build/test callers и текущей
документации. Сохранить интерфейсы, владение состоянием, протокольную и игровую
семантику, подготовку ресурсов и измерение submission timing. Новые слои
абстракции, wrappers или объединение реализаций для этого не требуются.

Исходный ориентир — коммит `c310cf2a7` (тикет 06). Перед реализацией зафиксировать
актуальный HEAD и рабочее дерево; последующие изменения и чужую работу сохранить.

## Целевая структура

Все пути в таблице относительны к `src/client/sv`. Обозначение `.[ch]`
означает перенос обоих существующих файлов `.c` и `.h`.

| Файлы | Назначение |
|---|---|
| `main.c`, `app.[ch]`, `result.[ch]` | Остаются в корне: запуск, сборка модулей/lifecycle и общий контракт результата SV |
| `session.[ch]`, `alerts.[ch]` | `session/`: модель сессии и реакции на её изменения |
| `protocol.[ch]`, `version.c`, `hp-update.h`, `message-update.h`, `key-request.h` | `protocol/`: wire decoding/serialization, версии и локальные baseline helpers |
| `input.[ch]`, `native-input.[ch]` | `input/`: router, контексты, макросы и адаптер SDL-ввода |
| `ui.[ch]`, `font.[ch]`, `status.[ch]`, `message-text.[ch]` | `ui/`: layout, rendering, ресурсы и подготовка представлений |
| `timing.[ch]` | `diagnostics/`: измерение времени до отправки кадра |

Каталоги группируют связанные реализации; они не меняют логические interfaces.
Например, размещение SDL-адаптера рядом с router не разрешает добавлять SDL
зависимость в headless router. `status.[ch]` относится к подготовке UI, а
семантические HP-данные остаются собственностью session model.

`hp-update.h` сейчас используется и protocol, и session: сохранить эту локальную
SV-зависимость явным include. Разделение helper на новые модули не входит в перенос.
Временный bootstrap/peer остаётся в `src/temporary/sv`, сценарии — в
`tests/sv/scenarios`; production-реализацию в тесты не переносить.

## Требования к переносу

1. Переместить файлы по таблице без изменения поведения и без оставленных
   дублирующих исходников или compatibility headers по старым путям.
2. Использовать явные пути includes относительно корня SV, например
   `session/session.h`, `input/input.h`, `ui/font.h`. Сохранить один include root
   `src/client/sv`; не добавлять каждый подкаталог в search path. Проверить
   относительные ссылки на существующий `src/common` после углубления файлов.
3. Обновить `src/makefile.sv`: списки production objects, prerequisite headers,
   создание вложенных каталогов, compilation rules и загрузку `.d` dependencies.
   Linux/MinGW outputs остаются раздельными и отражают вложенные пути.
   Чистая сборка не должна зависеть от старых плоских `.o` или `.d`.
4. Обновить всех активных потребителей путей/includes: production SV,
   `src/temporary/sv`, native scenarios, headless harnesses и Python runners.
   Найти потребителей поиском по репозиторию, а не ограничиваться известным списком.
5. Обновить текущие указатели на исходники и описание размещения в
   `docs/sv-architecture.md` и других затронутых документах. Исторические отчёты,
   хеши и результаты прошлых запусков сохранить как исторические; новые результаты
   записать отдельно с актуальной ревизией и ограничениями окружения.
6. Не менять legacy-клиент или common ради удобства переноса. Новые независимые
   предложения улучшений записывать в `docs/sv-improvements.md` отдельно.

## Проверки

Использовать существующие согласованные interfaces: production Application,
Session, input router и runnable native scenario. Assertions не ослаблять.
Новые тесты на само расположение файлов не нужны.

- Собрать Linux SV с `-Wall -Wextra -Werror` в новом пустом каталоге build outputs
  (или после безопасной очистки только относящихся к SV артефактов).
- Проверить incremental build: изменение вложенного header пересобирает
  соответствующих потребителей через compiler-generated dependencies.
- Запустить весь доступный SV regression suite по командам из
  [отчёта тикета 06](../sv-geometry-timing.md#repeatable-commands): на момент
  постановки 23 runner-вызова, включая headless sanitizers, legacy HP regression,
  native software/OpenGL, geometry TTF/PCF и timing с отрицательными контролями.
- Предпринять MinGW-сборку. При доступных зависимостях выполнить Wine smoke,
  включая software renderer. Отсутствующие зависимости/окружения записать как
  непроверенные, не выдавать за успешное выполнение.
- Проверить отсутствие старых путей в активных build/test/include callers,
  отсутствие случайных изменений legacy/common и сохранность посторонней работы.
- Выполнить Standards/Spec code-review относительно зафиксированного исходного
  HEAD, исправить замечания и записать результаты.

## Результат — 2026-09-22

Исходная ревизия `c310cf2a7567c239001c1d05d74c53eb7af4b6cb`, ветка
`modern_interface`. Перенесены 24 файла в `session/`, `protocol/`, `input/`,
`ui/`, `diagnostics/`. Сверка с исходной ревизией подтверждает: содержимое всех
перенесённых файлов совпадает после исключения строк `#include`. Root callers
и существующие сценарии изменены только для новых includes; headless runners
используют новые пути production sources. Assertions и публичные interfaces
не изменены. Старых копий и forwarding headers нет.

Linux SV собран с `-Wall -Wextra -Werror` в новом пустом
`/tmp/sv-arch003-linux-clean`, затем штатно в `.sv-build/linux/…`.
После обновления mtime `session/session.h` пересобрались ровно 20 объектов,
зависящих от него согласно `.d`; повторная сборка не пересобрала ни одного
объекта. Это проверяет реальные compiler-generated dependencies после переноса.
Содержимое заголовка при incremental-проверке не менялось.

Для повторения чистой сборки использовать новый каталог:

```sh
make -C src -f makefile.sv tomenet-sv SV_OUT="$(mktemp -d /tmp/sv-arch003-build.XXXXXX)"
```

Все 23 runner-вызова из отчёта тикета 06 прошли: четыре headless suites с
ASan/UBSan/LeakSanitizer, legacy HP, двенадцать прежних native checks на software
и OpenGL, четыре geometry TTF/PCF checks и два timing runner с отрицательными
контролями. Первый headless запуск был заблокирован ptrace-ограничением sandbox
для LSan; повтор выполнен вне sandbox без отключения sanitizers. Полный suite
также выполнен через штатную escalation с доступом к графической сессии.
Проверки старых путей в активных source/build/test callers прошли; одноимённый
`src/common/version.h` остаётся независимым неизменённым legacy-заголовком.

MinGW-сборка предпринята и остановлена проверкой отсутствующих cross SDL3,
SDL3_ttf и FreeType development dependencies. Wine smoke, включая software,
остаётся непроверенным. Прошлые ограничения физического DPI/Windows и human UX
acceptance из тикета 06 этим переносом не снимаются.

`dda366d39f22a64f3d78552b29c76e99d43f462715497b3319983f5527a5b1f1`.
Локальные временные логи: `/tmp/sv-arch003-build-clean.log`,
`/tmp/sv-arch003-build-default.log`, `/tmp/sv-arch003-build-incremental.log`,
`/tmp/sv-arch003-build-noop.log`, `/tmp/sv-arch003-incremental-result.log`,
