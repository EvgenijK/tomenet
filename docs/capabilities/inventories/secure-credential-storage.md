# Secure credential storage APIs

Research date: 2026-09-18. Prerequisite evidence for **Define credential storage policy**; this file proposes mechanisms, not additional product policy. Scope: Linux amd64 and Windows 10/11 i686 MinGW32. Documentation and installed headers only: no vault access, secret inspection, package installation, compilation, or runtime tests were performed.

## Verified Linux API facts

- libsecret is a C client library with `libsecret/secret.h`, pkg-config module `libsecret-1`, and GLib/GObject dependencies. A `SecretService` communicates with a Secret Service implementation; current libsecret also describes a portal-backed encrypted-file mode. Installing/linking the library alone does not establish that a usable desktop secret service exists. For the proposed ordinary desktop D-Bus path, the running user's service and bus are runtime prerequisites. [libsecret overview](https://gnome.pages.gitlab.gnome.org/libsecret/), [SecretService](https://gnome.pages.gitlab.gnome.org/libsecret/class.Service.html)
- Search attributes use case-sensitive equality and are **not secrets**; implementations may persist them unencrypted. Keep passwords and reversible representations out of names, labels, attributes and lookup keys. [Secret Service lookup attributes](https://specifications.freedesktop.org/secret-service/latest-single/#lookup-attributes)
- Binary APIs have existed since libsecret 0.19.0. `secret_password_storev_binary_sync()` accepts a `SecretValue`, cancellation object and `GError`; its boolean reports storage success. `secret_password_lookup_binary_sync()` returns a `SecretValue` or NULL. Inspect the error as well as the return value. [Binary store](https://gnome.pages.gitlab.gnome.org/libsecret/func.password_storev_binary_sync.html), [binary lookup](https://gnome.pages.gitlab.gnome.org/libsecret/func.password_lookup_binary_sync.html)
- `SecretValue` supports explicit data lengths; `secret_value_get()` supplies the byte count. Use these lengths rather than `strlen()` and release values with `secret_value_unref()`. Binary storage avoids imposing UTF-8 conversion on existing protocol credential bytes. [SecretValue](https://gnome.pages.gitlab.gnome.org/libsecret/struct.Value.html), [creation](https://gnome.pages.gitlab.gnome.org/libsecret/ctor.Value.new.html), [byte access](https://gnome.pages.gitlab.gnome.org/libsecret/method.Value.get.html)
- Unlocking one item may unlock its entire collection. The library handles service prompts, which the service displays; either user or client may cancel a prompt. A cancellation can race completion, so a caller must handle completion even while cancelling. No app-owned master-password dialog is required by these APIs. [Unlock](https://gnome.pages.gitlab.gnome.org/libsecret/method.Service.unlock_sync.html), [prompt protocol](https://specifications.freedesktop.org/secret-service/latest/prompts.html)
- Synchronous store, lookup, unlock and delete operations may block indefinitely and must not run on the UI thread. `GCancellable` supports cancellation; unlock returns the count and list actually unlocked, so lack of an error is not sufficient evidence that every requested item unlocked. [Binary store](https://gnome.pages.gitlab.gnome.org/libsecret/func.password_storev_binary_sync.html), [binary lookup](https://gnome.pages.gitlab.gnome.org/libsecret/func.password_lookup_binary_sync.html), [unlock](https://gnome.pages.gitlab.gnome.org/libsecret/method.Service.unlock_sync.html)
- **Deletion trap:** `secret_password_clear_sync()` removes only unlocked matches; its boolean means any item was removed. It cannot by itself prove all matching credentials are gone. `secret_item_delete_sync()` can prompt and exposes success/error. An implementation requiring reliable forgetting must discover matches including locked items and handle deletion/cancellation explicitly. [Password clear](https://gnome.pages.gitlab.gnome.org/libsecret/func.password_clear_sync.html), [item deletion](https://gnome.pages.gitlab.gnome.org/libsecret/method.Item.delete_sync.html), [locked/unlocked search results](https://specifications.freedesktop.org/secret-service/latest-single/#lookup-attributes)
- Secret Service does not mandate master passwords or application access control. Its presence does not prove encryption-at-rest details, isolation from code running as the same user, or a particular provider configuration. [Specification limits](https://specifications.freedesktop.org/secret-service/latest/ch10.html)

## Verified Windows API facts

- `CRED_TYPE_GENERIC` stores application-defined secret bytes. `CredentialBlobSize` is in bytes; current Microsoft documentation sets a 2560-byte maximum. `TargetName` plus `Type` identifies a credential; the target name is case-insensitive. `UserName` is ignored by Credential Manager for generic credentials. Do not rely on it to distinguish accounts. [CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)
- `CRED_PERSIST_LOCAL_MACHINE` means persistence across logons for **the same user on the same machine**, not sharing with all machine users. `CRED_PERSIST_SESSION` expires at logoff; enterprise persistence can roam when configured. [CREDENTIALW persistence](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)
- `CredReadW()` uses the current token's logon-session credential set. Pass flags zero, check BOOL and `GetLastError()`, and free returned allocation with `CredFree()`. Distinguish missing credential (`ERROR_NOT_FOUND`) from unavailable logon-session storage (`ERROR_NO_SUCH_LOGON_SESSION`). These documented desktop APIs predate Windows 10; this establishes API availability, not an exercised Windows 10/11 runtime result. [CredReadW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw)
- `CredWriteW()` creates or updates that user's credential; check BOOL and `GetLastError()`. Use flags zero for replacing the blob. `CRED_PRESERVE_CREDENTIAL_BLOB` is for retaining the old blob and requires input blob size zero. Errors include unavailable logon-session storage and invalid fields/flags. [CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew)
- `CredDeleteW(target, CRED_TYPE_GENERIC, 0)` returns success/failure with `GetLastError()`. `ERROR_NOT_FOUND` means absent; other errors must not be reported as successful deletion. [CredDeleteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-creddeletew)
- Header is `wincred.h`, import library `Advapi32.lib`, runtime DLL `Advapi32.dll`; for the local MinGW toolchain the corresponding import archive is present as `/usr/i686-w64-mingw32/lib/libadvapi32.a` (proposed linker flag `-ladvapi32`). Use explicit `W` functions for metadata; generic blob bytes need not be UTF-16. [Windows build requirements](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw), [generic blob contract](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)
- Scope is the user's credential set, not an application-owned security boundary. Do not advertise protection against arbitrary code executing with that user's access. This is a security inference from the user/logon-token contract, not a tested attack claim. [CredReadW scope](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw)

## Local header evidence and limits

Read-only checks found declarations for `CredReadW`, `CredWriteW`, `CredDeleteW`, `CredFree`, `CRED_TYPE_GENERIC`, and `CRED_PERSIST_LOCAL_MACHINE` in `/usr/i686-w64-mingw32/include/wincred.h`. **That installed header defines `CRED_MAX_CREDENTIAL_BLOB_SIZE` as 512**, unlike the current Microsoft documentation's 2560. Validate the application's encoded credential size against the actual supported toolchain limit; do not promise 2560-byte payload support merely from current online docs. `/usr/include/libsecret-1/libsecret/secret-value.h` also provides explicit-length value construction/access. These observations do not establish link success, provider availability, or vault behavior.

## Proposed mechanism and fallback implications

These are implementation recommendations for the policy decision owner to accept or revise:

1. Put a small OS-storage adapter behind load/store/delete operations. Linux: libsecret >= 0.19 with binary secret values and a persistent default collection. Windows: generic Credential Manager record, local-machine persistence, explicit `W` API calls. Store existing credential bytes without changing protocol encoding. Keep public identity metadata separate from the secret payload.
2. Use a stable application namespace plus an unambiguous opaque key. Account/server scoping must follow the agreed product policy; the API does not decide it. If deriving Windows keys from case-sensitive identities, encode them so Windows case-insensitive target matching cannot merge distinct identities.
3. Keep UI responsive through a worker or properly integrated asynchronous operations. Model unavailable, missing, locked/prompting, cancelled, failed and success outcomes as needed; do not reduce every unsuccessful lookup to “no saved password.” Late completion after cancellation must not unexpectedly submit credentials or mark storage successful.
4. Do not let storage failure convert a successful game login into login failure. Report that remembering failed; retain only the session data needed for the active login. Do not create a plaintext fallback or overwrite a known good secret after failed authentication. Deletion failure must leave the UI honest about possible retained secrets.
5. If launching without libsecret installed must remain supported, direct mandatory dynamic linking alone cannot supply that behavior: package the dependency or load the backend optionally and treat absence as unavailable. A missing/locked/cancelled/unusable provider should lead to manual entry for the current session, not an automatic change of storage format. Choosing provider/package support and retry behavior remains product/packaging policy.
6. Future implementation verification should use synthetic bytes and adapter fault injection plus opt-in OS integration checks in disposable test vaults. No real credential material is needed to verify serialization, error propagation or UI state handling.

These mechanisms avoid a new plaintext credential file; they neither erase an existing legacy plaintext copy nor make its contents secure. Handling that legacy copy is a separate scope decision.
