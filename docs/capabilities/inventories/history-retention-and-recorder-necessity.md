# History retention and recorder necessity: source-backed assessment

Research for [Assess history retention and recorder necessity](../issues/19-assess-history-retention-and-recorder-necessity.md), 2026-09-14. Planning evidence from the current checkout; no implementation, runtime parity claim, recording format, storage budget or privacy/product policy is established here. Local source is sufficient: the question concerns this client and already agreed contracts, not SDL API facts. No branch switch was made in the shared checkout.

## Finding

Behavior requires several bounded working histories, but does not establish a need for a full session recorder. Message recall and input recall are actual user capabilities. Ordered transient effects need delivery, current documents need lossless content, and special stores need sufficient logical canvas/animation state for reconstruction. These requirements do not imply retention of every past packet, page, operation or input. The proposed minimum below is a consequence of observable baseline plus the agreed model boundary, and is explicitly distinguished from an approved retention policy.

[Choose the presentation-state boundary](../issues/02-choose-presentation-state-boundary.md), Answer/State lifetime and Decode, ordering and publication, already requires: UI reconstruction preserves interaction state; events have separate identity and order; teardown separates session identities; full recording is separate and explicit; credentials and arbitrary privileged file payloads do not enter ordinary presentation events. [Map every packet field to semantic state](../issues/11-map-every-packet-field-to-semantic-state.md), Answer, requires lossless envelopes before bounded legacy decoding loses information and retention on the lifetime of the owning snapshot/event. [Inventory formatted and server-driven surfaces](../issues/12-inventory-formatted-and-server-driven-surfaces.md) requires original formatted content alongside parsed projections. None authorizes an unlimited archive.

## Important non-equivalences

Message **storage** deduplication shares the byte offset of an identical recent string but still advances the next pointer and creates another occurrence slot ([c-util.c:4113](../../../src/client/c-util.c#L4113), [c-util.c:4133](../../../src/client/c-util.c#L4133)). It is not event coalescing. Input recall intentionally removes older identical text before append ([c-util.c:3356](../../../src/client/c-util.c#L3356)). Recall/export renderers may further filter noise and format repetitions; parity is their observed outcome, not a license to merge newly arrived effects ([c-xtra2.c:144](../../../src/client/c-xtra2.c#L144), [c-xtra2.c:1018](../../../src/client/c-xtra2.c#L1018)).

Session teardown invalidates old pending requests/events, but does not imply clearing process-level message recall: the baseline intentionally repaints retained messages across login. Preserve historical collection identity separately from delivery-session identity. The comment near chat loading claims message log reset elsewhere; the actual relog reset block is disabled, so that comment cannot establish a universal clear policy ([c-init.c:4483](../../../src/client/c-init.c#L4483), [c-init.c:4574](../../../src/client/c-init.c#L4574), [c-util.c:4803](../../../src/client/c-util.c#L4803)).

Canvas compaction must not replay consumed sounds, restart finished animations, or convert a force-clear into ordinary character clearing. A current checkpoint is a logical lossless representation, not a screenshot. Animation intermediate randomness is local; exact-frame replay needs more than server animation parameters ([nclient.c:5068](../../../src/client/nclient.c#L5068), [nclient.c:5110](../../../src/client/nclient.c#L5110)).

## Disk behavior and sensitive-data boundary

Existing persistence is heterogeneous, not a general recording system. Quit may prompt/export chat or all messages based on `save_chat`, always calls nonempty chat-input save, and saves guide bookmarks ([c-init.c:3349](../../../src/client/c-init.c#L3349), [c-init.c:3446](../../../src/client/c-init.c#L3446), [c-init.c:3459](../../../src/client/c-init.c#L3459)). Chat export actually selects important-scrollback messages, including chat, not only chat text. Received private notes automatically append timestamped, stripped text to `user/notes-<account>.txt`, including continuation lines ([nclient.c:3355](../../../src/client/nclient.c#L3355)). These are distinct capabilities; recorder disabled must not silently alter their independently governed behavior.

SDL3 chat/bookmark **save** uses `ANGBAND_DIR_USER`, but **load** uses `os_temp_path`; non-SDL3 load uses user directory. Temporary root can come from environment or user-root temp. This asymmetry is a source fact, not a chosen migration repair ([c-init.c:3393](../../../src/client/c-init.c#L3393), [c-init.c:3419](../../../src/client/c-init.c#L3419), [c-init.c:4485](../../../src/client/c-init.c#L4485), [c-init.c:4501](../../../src/client/c-init.c#L4501), [common.c:322](../../../src/common/common.c#L322)). See [Persisted settings and files](persisted-settings-and-files.md) and the **current Answer** of [Define settings and migration boundary](../issues/05-define-settings-and-migration-boundary.md): compatible SDL3 files are shared for read/write; settings/personal data/password are included in explicit external data-only import. The earlier independent-copy proposal is superseded. Historical confirmed discussion includes personal data by default; this investigation does not change that authorization. [Specify persistence ownership and UI configuration schema](../issues/25-specify-persistence-ownership-and-ui-configuration-schema.md) owns exact history/bookmark paths, precedence, reimport and concurrency, not assumptions based on `.tmp` or export filenames.

Raw transport/input recording can expose account identity and credentials: verification sends `real,nick,pass`, relogin receives account name/password, password change sends old/new values ([nclient.c:1430](../../../src/client/nclient.c#L1430), [nclient.c:2053](../../../src/client/nclient.c#L2053), [nclient.c:8154](../../../src/client/nclient.c#L8154)). Private prompt input is deliberately excluded from recall and password-change temporaries are wiped ([c-util.c:2641](../../../src/client/c-util.c#L2641), [c-util.c:13163](../../../src/client/c-util.c#L13163)). Incoming notes/messages and ordinary drafts/macros may also contain personal/private text. Privileged file packets carry arbitrary payload, so packet capture must not bypass the already agreed separate control channel ([nclient.c:477](../../../src/client/nclient.c#L477), [nclient.c:650](../../../src/client/nclient.c#L650), [presentation boundary](../issues/02-choose-presentation-state-boundary.md)).

Consequently, a recorder proposal cannot authorize persistent credentials, private prompt values, raw privileged file payloads, private conversations/notes, identity, or arbitrary user input merely by being called “debugging.” The existing boundary already excludes credentials/file payloads from ordinary events; any separately persisted sensitive data needs explicit policy covering scope/defaults/consent, location, retention/deletion, sharing and fixtures. This research supplies exposure facts, not consent or encryption decisions. Sanitization can invalidate exact-wire replay; sanitized fixtures must say what remains asserted.

## Recorder disabled and acceptance followups

Proposed minimum off behavior: no recording file or accumulating replay archive; working model, bounded recall, owning lossless payloads, event delivery, canvas reconstruction, macro recording and independently specified exports/notes/bookmarks still work. Recorder failure/full disk must not gate decoding, command replies, active-state retention or combat repaint. A memory diagnostic ring is still a recorder and needs explicit enablement/bounds if proposed; “off” is not hidden unlimited RAM recording.

The existing acceptance question should now specify:

1. Recorder choice: fixtures only, test-only bounded capture, optional shipped bounded capture, or fuller recording with justified unique evidence. State whether determinism means semantic outcomes, outgoing replies, effect counts/order, or exact frames/timing; wire-only fixtures cannot prove all four.
2. Named consumer registration/recreation/cursor rules, acknowledgements, slow-consumer overflow/backpressure and session invalidation. Check duplicate identical events, pending request/reply exactly once, cross-login recalled messages without redispatch, UI recreation mid-page and mid-animation, forced clears over graphics and unknown operations.
3. Proven compaction/checkpoint equivalence, capacity/byte-pressure boundaries, stable read-view ownership during eviction, incomplete packet rollback and decode failure. Test state updates while an unrelated document/batch is incomplete.
4. Recorder-off and recorder-failure equivalence for gameplay/recall/repaint/replies; bounded-memory runs with many replaced pages/canvas writes/events; no replay-buffer growth when off. Stress full disk only if shipped capture is selected.
5. Complete synthetic fixtures for the existing packet/formatted ledgers, with source/version/features and initial-state provenance. Do not rely on live accounts/private traffic; demonstrate sensitive controls cannot enter ordinary event/fixture capture and document limitations of sanitization.

[Specify persistence ownership and UI configuration schema](../issues/25-specify-persistence-ownership-and-ui-configuration-schema.md) should preserve the already approved common-file sharing and personal import scope, and specify chat input/export/private-note/bookmark load/save defaults, SDL3 path asymmetry disposition and exact import/write behavior. [Define credential storage policy](../issues/24-define-credential-storage-policy.md) already owns credential diagnosis/export restrictions. Any elected diagnostics need explicit sensitive-data scope and retention/sharing policy; do not reopen approved personal import inclusion merely because runtime retention is investigated. Runtime histories should not be equated with imported personal files.

Newly sharp cross-cutting question: **Which bounded working-retention and optional-capture contract is normative for tomenet-sv?** It includes consumer low-watermark/overflow, checkpoint eligibility for unknown canvas operations, cross-login recall identity, and whether any shipped recorder exists. These are not fully answered by generic acceptance scenarios or disk import policy. A focused HITL decision ticket is warranted if the research ticket cannot itself approve this contract; then link it to acceptance and privacy/persistence, and keep numeric resource budgets as map fog until interfaces/harness expose measurements. No implementation task or full-recorder assumption should be created from this finding.
