# Кодовая архитектура TomeNET SV: варианты границ модулей

Статус: исследование для обсуждения, 2026-09-20. Не ADR и не утверждённый план реализации.
Исходный запрос: разграничить функциональность модулей; события предложены как возможное средство.
Сравнение опирается на существующий behavior baseline.

Итог интервью Q4–Q14 собран в [архитектуре SV](../sv-architecture.md)
и подтверждён пользователем на финальной сверке 2026-09-21.
Этот файл сохраняет сравнение вариантов и основания рекомендаций.

## Согласованные критерии — 2026-09-21

В раунде Q4 согласованы приоритеты: перенос игровых возможностей и дальнейшая
переработка UX. Игровые правила должны проверяться отдельно от интерфейса;
изменение компоновки или способа ввода не должно требовать переделки сетевой логики.
В раундах Q5–Q6 согласованы разделение модели сессии, игровых взаимодействий, UI
и протокола и переработка legacy-сценариев по одной возможности с сохранением поведения.
Решение: [ADR-0001](../adr/0001-separate-session-interactions-and-ui.md).
В Q8 согласован один владелец состояния сессии и взаимодействий в главном потоке;
фоновые задачи возвращают результаты без самостоятельного изменения этого состояния.
Решение: [ADR-0002](../adr/0002-main-thread-state-ownership.md).
В уточнённом Q7 согласованы явные связи между крупными модулями и локальная детализация
действий, без центрального switch на все игровые ситуации и без обязательного единого
механизма доставки. Решение: [ADR-0003](../adr/0003-explicit-module-connections.md).
Конкретные интерфейсы и контракты доставки пока обсуждаются.

В Q9 согласован отдельный модуль предупреждений: он получает смысловое изменение
игровых данных, настройки и необходимый контекст внимания игрока и решает, нужны ли
звук или сообщение. Он не зависит от SDL, геометрии и конкретных элементов UI;
модель сессии не принимает на себя эти межмодульные правила.
Точное соответствие контекста внимания legacy off-panel условиям ещё надо определить.

В уточнённом Q11 согласованы версии изменений по областям состояния и производные
кэши UI, с чтением больших представлений только в фазе построения кадра.
Решение: [ADR-0004](../adr/0004-revision-based-ui-views.md).
В Q10 согласовано полное последовательное применение каждого входа и передача
результатов исполнителям до следующего входа, без ожидания завершения внешней работы.
Отрисовка независима, значимые промежуточные реакции сохраняются; очереди нужны
только для откладывания. Контракт дополнен в ADR-0003.

В Q12 согласованы поколение сессии для относящихся к ней взаимодействий и фоновой
работы, отмена при закрытии и отбрасывание запоздавших результатов;
общие ресурсы приложения живут независимо ([ADR-0005](../adr/0005-session-scoped-work.md)).
В Q13 согласован бюджет обработки входов за проход цикла с возвратом управления UI
между целыми входами, сохранением порядка сети и ограниченными буферами без
молчаливого удаления игровых обновлений (дополнение ADR-0002).
В Q14 согласованы изоляция необязательных отказов, предусмотренное протоколом
восстановление и явное завершение сессии при невозможности сохранить корректность
или обязательные данные ([ADR-0006](../adr/0006-errors-and-overload.md)).

## Вывод для обсуждения

Рекомендация: явные интерфейсы модулей, один владелец каждого изменяемого состояния,
направленный поток входов и результатов, смысловые представления данных для UI.
События полезны для некоторых результатов обработки; глобальная шина для этой цели пока не нужна.
Многошаговые взаимодействия стоит описывать отдельными машинами состояний.
Это комбинация приёмов, а не выбор между взаимоисключающими «слоями» и «событиями».

Критерий успеха предлагается проверять на изменении возможности: где меняется правило,
какие модули приходится понимать и можно ли проверить результат без настоящего окна/сервера.
Сокращение числа прямых вызовов само по себе такого результата не доказывает.

## Что уже известно о клиенте

- `SvSession` скрыт за opaque C type; владеет `player_type`, версией протокола,
  входным/выходным буфером и HP metadata. UI получает копию `SvStatus`;
  обработка и rendering имеют одного владельца-поток.
  Источники: [session.h](../../src/client/sv/session.h), [session.c](../../src/client/sv/session.c).
- Работающая реализация синтетическая: HP проходит общий decode/apply, live transport,
  чат и запросы ввода ещё не реализованы. Предупреждения HP остаются только в legacy path.
  Источник: [sv-hp.md](../sv-hp.md).
- Текущий main получает SDL events и рисует кадры; это ещё не готовый цикл живой сессии.
  Источник: [main.c](../../src/client/sv/main.c).
- Legacy входы включают вложенные prompt loops, макросы, разные политики клавиш,
  отмену, возврат focus и ожидания с обработкой сети. Простое `key → action` недостаточно.
  Источник: [аудит ввода](single-window-input-loops.md#result).
- Протокол содержит текущие значения, коллекции, batch/clear markers, запросы ответа
  и упорядоченные сообщения/эффекты. Эти данные уже требуют разных правил lifecycle.
  Источник: [аудит packet state](single-window-packet-state.md#state-authority-and-ownership).
- Текущий словарь разделяет `Session presentation model`, `Input router`, `Action`
  и `Presentation state`. Предлагаемые границы развивают это разделение.
  Источник: [CONTEXT.md](../../CONTEXT.md).

## Что именно означают события

В этом исследовании используются рабочие различия:

| Понятие | Смысл | Пример |
|---|---|---|
| Action / command | Намерение, которое ещё может быть отклонено | Выпить выбранное зелье |
| Decoded change | Полностью декодированное входное изменение | Сервер сообщил HP 10/100 |
| State / view | Что известно сейчас | Текущий HP, список сообщений, активный запрос |
| Notification | Сообщение о случившемся | Изменился статус сессии |
| Effect | Запрос на внешнее действие | Отправить ответ, проиграть предупреждение |

Это смысловые контракты. Прямой вызов, callback, очередь и mailbox — способы доставки.
В описании Observer у автора Game Programming Patterns уведомление синхронно вызывает
получателей; очередь добавляет разделение по времени и нужна, когда это разделение полезно.
Автор отдельно предупреждает о глобальности центральной очереди.
Источники: [Observer](https://gameprogrammingpatterns.com/observer.html),
[Event Queue](https://gameprogrammingpatterns.com/event-queue.html).

Event sourcing дополнительно сохраняет последовательность изменений для восстановления
состояния. Наличие callbacks или очереди такой гарантии не даёт.
Источник: [Martin Fowler, Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html).
Рекомендация: не вводить event sourcing без отдельной потребности; тестовые последовательности
входов и проверяемые результаты можно иметь без журнала всей жизни приложения.

## Сравнение вариантов

Оценки применимости и затрат ниже — выводы этого исследования для SV, не внешние факты.

| Вариант | Что даёт здесь | Цена / ограничение | Предварительная оценка |
|---|---|---|---|
| Явные C-интерфейсы + владельцы состояния + views + адресные effects | Понятный путь от входа к изменению; естественное развитие `SvSession`; переиспользование функций | Нужны содержательные границы, иначе session станет свалкой правил | Основа |
| Глобальный publish/subscribe bus | Новый независимый слушатель подключается без изменения издателя | Подписки скрывают обязательные зависимости; нужны правила порядка, удаления, повторного входа и payload lifetime | Не вводить по умолчанию |
| Messages → update → state/effects → view | Явные переходы, удобные проверки сценариев, отделение I/O | Единый универсальный reducer рискует разрастись; полное immutable копирование не соответствует текущему C-коду | Применить принцип к взаимодействиям и нужным границам |
| ECS | Данные сущностей и обработка групп компонентов | Не отвечает напрямую на владение transport, prompts, чат и lifecycle | Рассматривать локально при появлении подходящей задачи |
| Actors / модули с отдельными потоками | Изоляция медленной работы и обмен сообщениями | Очереди, остановка, устаревшие результаты и синхронизация усложняют текущую модель | Только по установленной потребности |

В Elm Architecture разделены Model, View и Update; внешние действия описываются `Cmd`/`Sub`
и исполняются runtime. Это первичный пример направленного потока, а не требование использовать Elm.
Источники: [Architecture](https://guide.elm-lang.org/architecture/),
[Commands and Subscriptions](https://guide.elm-lang.org/effects/).

В Flecs ECS world хранит сущности и компоненты, системы выполняют callbacks по query.
В Erlang каждый процесс имеет свою очередь сообщений; это пример организации обмена,
но не основание отождествлять actor с одним системным потоком.
Источники: [Flecs Quickstart](https://www.flecs.dev/flecs/Quickstart.html),
[Erlang Concurrent Programming](https://www.erlang.org/doc/system/conc_prog.html#message-passing).

## Предлагаемое распределение ответственности

Это эскиз для обсуждения, не окончательный список файлов или API.

| Модуль / граница | Владеет | Скрывает от остальных |
|---|---|---|
| Transport и protocol adapter | Соединение, framing/partial input, negotiated wire variant | Socket API, версии и особенности пакетов |
| Session presentation model | Session-derived значения, коллекции и lifecycle запросов | Legacy storage и атомарность применения обновлений |
| Input router + владельцы взаимодействий | Binding/context, незавершённый локальный ввод, переходы prompt flow | Физические клавиши, вложенность выбора и отмены |
| UI / renderer | Layout, локальные selections/scroll, графические ресурсы | SDL rendering и геометрию |
| Предупреждения | Правила реакции на игровые изменения с учётом настроек и контекста внимания | Условия возникновения звука или сообщения |
| Audio / внешние исполнители | Playback и выполнение адресных effects | API устройств и другой внешний I/O |
| Application / lifecycle coordinator | Создание/закрытие сессии и порядок работы модулей | Сборку зависимостей и переходы между режимами клиента |

Направление: вход → ответственный модуль → обновлённые данные и результаты → UI/исполнители.
Один владелец сессии не означает один огромный `session.c`: статус, сообщения, инвентарь
могут иметь приватные подмодули с собственными правилами внутри session lifetime.
Не нужно заранее дробить каждый struct в новый модуль или переносить каждый helper в reducer.

Форма API должна позволять видеть обязательного получателя из места сборки клиента.
Например, coordinator передаёт результат предупреждения аудиомодулю; сам HP handler
не зависит от SDL audio и не ищет слушателей в глобальном registry.
Опциональные observers уместны, если действительно нужны независимые подписчики;
их lifetime и допустимые действия при callback должны быть частью контракта.

## Проверка границ на сценариях TomeNET

**HP и предупреждения.** После полного decode модель применяет HP и предоставляет
смысловое изменение. Модуль предупреждений вычисляет реакции по правилам baseline
с учётом настроек и контекста внимания; renderer читает последнее значение HP.
При HP `50 → 10 → 50` между кадрами полоса может сразу показывать 50,
но предупреждение для 10 не должно исчезнуть из-за чтения только финального snapshot.
Legacy `alert_hitpoint` срабатывает на каждый принятый HP packet ниже порога,
а не только при пересечении порога; off-panel damage отдельно учитывает предыдущий HP и drain.
Источник: [Receive_hp](../../src/client/nclient.c#L2171).
Предлагаемый effect должен сохранить решение и необходимые данные в момент обработки;
audio consumer не должен заново вычислять его по более позднему HP.

**Чат.** История — упорядоченная коллекция с владельцем; два одинаковых сообщения
могут быть двумя отдельными поступлениями. Панель истории и live feed читают её views;
уведомление о новом сообщении, если нужно, доставляется отдельно.
Нельзя сводить вход к одному полю `last_message`; clear/topline control тоже не обычный append.
Основание: [message и ordered event rules](single-window-packet-state.md#clear-replace-and-batch-sentinels).

**Многошаговая команда.** Для «выбрать предмет → направление → отправить» предлагается
явное состояние взаимодействия, которое принимает следующий ввод и возвращает новый prompt
или команду. Между шагами главный цикл продолжает принимать HP, чат и disconnect.
Устаревший выбор перепроверяется перед отправкой; отмена возвращает контекст владельца.
Конкретные правила должны переноситься из соответствующего baseline flow, включая макросы,
raw-key fallback и серверные запросы; общий reducer не заменяет этот аудит.
Основание: [input contexts](single-window-input-loops.md#atomic-loop-inventory).

**Disconnect.** Предлагается один явный lifecycle transition: запрет новых отправок,
отмена активных взаимодействий, освобождение session-owned ресурсов и переход UI.
Coordinator знает, что выполнить обязательно; эффект «показать причину» может быть отдельным.
Для асинхронных jobs нужны session generation и отбрасывание результатов закрытой сессии.
Текущий `failed` флаг ещё не реализует такой полноценный lifecycle.
Основание: [session.c](../../src/client/sv/session.c), [quit/relogin ledger](single-window-packet-state.md).

**Переиспользование legacy.** Разделять проверенную семантику decode/apply и конкретные
терминальные последствия. HP уже показывает такой шов: общий helper используется обоими
клиентами; SV не требует наследовать `Term` и globals.
Для других функций сначала проверить побочные действия и зависимости, затем выделять шов;
обёртка «опубликовать событие» вокруг прежней блокирующей функции этого не исправит.
Основание: [hp-update.h](../../src/client/hp-update.h), [ownership notes](../sv-hp.md#ownership-and-production-boundary).

## Потоки, очереди и стоимость views

SDL3 требует main thread для `SDL_PollEvent` и `SDL_RenderPresent`.
Это ограничение SDL не запрещает выносить сетевой I/O в worker.
Источники: [SDL_PollEvent](https://wiki.libsdl.org/SDL3/SDL_PollEvent),
[SDL_RenderPresent](https://wiki.libsdl.org/SDL3/SDL_RenderPresent).
Рекомендация: пока сохранить одного владельца модели и UI, предусмотреть неблокирующий transport;
решать вопрос worker по измеренным задержкам, особенностям платформы и обязательным операциям.

Snapshot означает согласованное представление, а не копирование всей карты и истории каждый кадр.
По Q11 малый HP snapshot возвращается значением, а большие представления доступны
только для чтения в фазе построения кадра без изменения модели. UI проверяет версии
областей состояния и обновляет производные кэши при изменении данных или входов
представления (шрифт, масштаб, геометрия). Заимствованные указатели не сохраняются
между кадрами; детализация изменений уточняется по измерениям.
Промежуточные views можно пропускать только после обработки всех значимых переходов.

Если effects отложены, нужны bounded storage, порядок, владение payload и явная реакция
на переполнение. Чат, ответы сервера и предупреждения нельзя молча сливать по одинаковому типу.
Обработчик не должен рекурсивно изменять session через цепочку callbacks;
новое намерение принимается в следующей установленной точке обработки.
Очередь и граница фазы должны появляться там, где нужно откладывание, а не для каждого вызова.

## Что ещё надо решить

1. Какие конкретные интерфейсы реализуют принятые границы ответственности?
2. Как контекст внимания для модуля предупреждений сохраняет legacy off-panel семантику?
3. Какие конкретные операции требуют исключений с отложенной доставкой по контракту Q10?
4. Какие размеры буферов и бюджеты работы подтверждаются измерениями? Политика ошибок согласована в Q14, lifecycle — в Q12.

Практический следующий шаг: разобрать три контракта на бумаге — HP с предупреждением,
входящий чат и многошаговый выбор с отменой/disconnect. Принятые принципы записаны в ADR выше;
контракты, ещё не согласованные в интервью, остаются предложениями.
Производительность альтернатив здесь не измерялась; live loop и полная совместимость не проверялись.
