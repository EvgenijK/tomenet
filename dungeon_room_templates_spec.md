# Шаблоны комнат в генерации данжей — согласованные требования

Статус: проект спецификации по результатам обсуждения. Код не изменён. Номера ниже соответствуют вопросам обсуждения; решения 1–143 и уточнения 20а, 46а, 46б, 62а, 77а, 78а приняты с описанным ниже пересмотром первой версии. Для редактора приняты условие Q144 о размещении в полном репозитории, способ загрузки игровых справочников Q144а и ответы пользователя на вопросы 146 и 151. Решения о редакторе 145, 147–150 и 152–153 выбраны ассистентом по поручению пользователя. Общая структура шаблона и основные правила текстового формата определены; наборы полей профилей монстров, предметов и шаблона комнаты для первой версии закрыты решениями 111, 135 и 138.

## Назначение

Шаблон комнаты — описанный в данных фрагмент уровня (например, лагерь орков, крипта или гнездо драконов) с заданной формой и фиксированными позициями клеток, монстров и предметов. Шаблон содержит три совмещённые карты: рельефа, монстров и предметов. Прямоугольная карта рельефа может содержать прозрачные клетки: они не меняют исходный уровень. Шаблон комнаты не требует стены по периметру и не получает свойства vault, связанные с постоянными стенами или запретом телепортации.

**Пересмотр правил сущностей для первой версии.** После решений 1–61 пользователь отказался от последовательных вариантов и произвольных запасных альтернатив в профилях монстров и предметов. Один профиль, обозначенный одним символом карты, задаёт одно правило выбора. Если по этому правилу монстра или предмет нельзя выбрать, создать либо поставить точно в назначенную клетку по любой причине, пропускается только эта сущность; шаблон комнаты остаётся. При неудаче с уникальным действует встроенная попытка обычной замены по решениям 99 и 107: для неё убирается только `flag:UNIQUE`, остальные фильтры сохраняются. Ограничения доступности и глубины продолжают действовать на каждую сущность. Ошибочный файл по решению 56 не загружается; невозможность разместить форму terrain остаётся причиной не ставить весь экземпляр.

## Принятые решения

1. **Область применения (уточнено решением 80).** Шаблоны комнат создаются на случайных неразрушенных этажах данжей, где выполняется обычный цикл построения комнат и шаблон помещается целиком. Это включает cavern, empty, small и `tiny_level` при выполнении указанного условия; для `tiny_level` действуют особенности решения 79. Обязательные maze-этажи, города внутри данжей, ветки с фиксированной картой, разрушенные этажи и поверхность исключены. Таким образом, одного наличия цикла комнат недостаточно для разрушенного этажа. В текущей генерации цикл комнат пропускается для обязательного `DF1_MAZE` ([`generate.c`](src/server/generate.c#L9144)); для разрушенных этажей действует отдельная ветка до выбора необычных комнат по решению 80.

2. **Содержимое.** Карта terrain задаёт только рельеф. Соответствующие позиции отдельных карт монстров и предметов задают фиксированные клетки их размещения и ссылаются на профили выбора сущностей. Результат выбора не меняет позицию исходной сущности: монстр или предмет либо появляется в указанной клетке, либо отсутствует согласно пересмотренному решению 5. Стандартные группы и эскорты исходного монстра могут добавить спутников в соседних клетках по решению 71. Подробное разделение карт закреплено в решениях 26 и 30.

3. **Входы.** Входы необязательны и задаются отдельным списком координат согласно решению 29. Если они есть, с остальным уровнем нужно соединить хотя бы один вход. Если входов нет, соединение не требуется.

4. **После генерации.** После завершения генерации уровня на шаблон комнаты действуют обычные игровые механики: монстры могут перемещаться и появляться, а эффекты игры могут менять рельеф.

5. **Неудачное размещение (пересмотрено для первой версии).** Если базовую расу монстра нельзя выбрать, создать либо поставить точно в указанную клетку, пропускается только этот монстр; шаблон комнаты сохраняется. Неудача применения эго сама по себе не пропускает базового монстра по решениям 68–69. При неудаче с уникальным сначала применяется встроенная обычная замена по решениям 99 и 107; если она тоже не удалась, клетка остаётся без монстра. Если предмет нельзя выбрать, создать либо поставить точно в указанную клетку, пропускается только предмет. Переносить сущность в соседнюю клетку нельзя. Некорректный файл отклоняется при загрузке по решению 56, а невозможность корректно разместить форму terrain исключает постановку всего экземпляра. Частично нанесённый terrain при такой неудаче не остаётся.

6. **Независимость от vault.** Флаг данжа `NO_VAULTS` сам по себе не запрещает шаблоны комнат. Для них нужен отдельный запрет. В коде существующий флаг — `DF3_NO_VAULTS` ([`defines.h`](src/common/defines.h#L7687)).

7. **Телепортация этажа.** Шаблоны комнат разрешены на этажах, где телепортация уже запрещена правилами самого этажа. Сам шаблон комнаты запрет телепортации не устанавливает.

8. **Частота и повторы.** Частота шаблонов комнат определяется в существующем выборе **очень необычных комнат** аналогично vault, с зависимостью от глубины и существующего `cfg.dun_unusual` по решениям 77 и 77а. Новая настройка `ROOM_TEMPLATE_CHANCE` и независимый плоский процент на каждую попытку не вводятся. Жёсткого ограничения на общее число экземпляров на этаже и запрета повторного выбора одного шаблона нет; фактическое размещение ограничивается пригодным местом и числом попыток генерации.

9. **Доступность шаблона (пересмотрено решением 83).** В файле шаблона могут задаваться собственные ограничения глубины по решению 84; допустимость по размеру зависит от конкретного этажа с учётом восьми ориентаций из решения 85. В первой версии файл шаблона не содержит условий по данжам. Доступность конкретных шаблонов для данжа определяется только списком разрешения или запрета в `d_info.txt` и общим флагом `NO_ROOM_TEMPLATES` по решениям 15 и 82–83.

10. **Ориентация (пересмотрено решением 85).** В первой версии для каждого шаблона всегда доступны все восемь ориентаций: четыре поворота исходной формы и четыре поворота её отражения. Автор не может ограничить этот набор через файл. В одной попытке построения комнаты ориентации выбранного шаблона перебираются в случайном порядке на одном блоке до первого пригодного варианта либо исчерпания восьми по решению 76. Vault уже применяет поворот и два отражения при построении ([`generate.c`](src/server/generate.c#L4405)).

11. **Нанесение на карту (дополнено решениями 136–137).** Активные клетки шаблона заменяют рельеф в своём месте аналогично vault и всегда получают `CAVE_ROOM`; прозрачные клетки не меняют **ничего** в соответствующих клетках уровня, включая флаги клетки и освещение. Для резервирования места нужен отдельный аналог `room_alloc()`, который не вызывает `check_room_boundary()`: тот может заполнить полом весь прямоугольник, включая прозрачные клетки ([`generate.c`](src/server/generate.c#L2028), [`generate.c`](src/server/generate.c#L2114), [`generate.c`](src/server/generate.c#L2177)). Шаблон комнаты не наследует свойства постоянных стен, запрета телепортации и `CAVE_ICKY` от vault. Освещение активных клеток следует стандартным правилам этажа и рельефа; отдельного `P:light` нет.

12. **Несколько входов.** При наличии нескольких меток достаточно соединить один вход; соединять все не требуется. Это уточнение решения 3.

13. **Уникальный монстр (пересмотрено решениями 101 и 105–107).** Поля `unique:yes` и `unique:no` удалены. Чтобы целенаправленно выбрать уникального, автор использует обычный требуемый флаг `M:<символ>:flag:UNIQUE` по правилам 95 и 100. Без него действует стандартный шанс уникального по решению 105; отдельного способа принудить только обычного монстра нет, кроме неявного отбора обычных для `ego:required` и `ego:exact`. При `flag:UNIQUE` поле `ego` игнорируется и для уникальной попытки, и для обычной замены по решению 106. Если уникального нельзя поставить, выполняется одна встроенная попытка обычной замены: `UNIQUE` удаляется из фильтров, остальные флаги, `glyph` и `level` сохраняются, `only_r_idx` игнорируется по решению 107. Вид из исходного уникального не выводится автоматически по решению 99.

14. **Обычное заполнение этажа.** После нанесения шаблона комнаты обычная генерация уровня может добавить монстров, предметы или лестницы на его свободные активные клетки, как это возможно для vault. Группы и эскорты основных монстров шаблона комнаты создаются отдельным этапом после постановки всех основных монстров по решению 72; они также могут занять допустимые клетки вне активной формы. В существующем коде размещение обычных лестниц и предметов проходит позднее ([`generate.c`](src/server/generate.c#L9387), [`generate.c`](src/server/generate.c#L9823)).

15. **Правило данжа.** Списки разрешённых или запрещённых шаблонов задаются повторяемыми строками `I:+:<код>` либо `I:-:<код>` в `d_info.txt` по решению 82. Без списка для данжа допустимы все шаблоны каталога, удовлетворяющие ограничениям глубины и размера; собственных условий по данжам в файлах шаблонов нет по решению 83. Списки разрешения и запрета взаимоисключающие в пределах одного данжа; смешение или ссылка на неизвестный код считаются ошибкой загрузки. Общий флаг `NO_ROOM_TEMPLATES` имеет приоритет над списком.

16. **Тематические данжи.** Список конкретных шаблонов из `d_info.txt` выбирается по эффективной теме этажа; общий `NO_ROOM_TEMPLATES` проверяется у реального экземпляра данжа. В файлах самих шаблонов условий по данжам нет по решению 83. В существующей генерации эффективный тип уже определяется с учётом `theme` и IDDC ([`generate.c`](src/server/generate.c#L7179), [`generate.c`](src/server/generate.c#L8640)).

17. **Выбор шаблона.** На неразрушенном этаже после двух проверок `rand_int(DUN_UNUSUAL) < dun_lev` шаблон комнаты участвует в общем выборе типа очень необычной комнаты вместе с vault, гнёздами и ямами по уточнению 77а **только если для текущего данжа и глубины есть хотя бы один разрешённый шаблон, который по габаритам может поместиться на этаже хотя бы в одной из восьми ориентаций** по решениям 78а и 85. Если таких шаблонов нет, исходный розыгрыш старых типов остаётся без изменений. Если выбран тип «шаблон комнаты», среди допустимых шаблонов выполняется взвешенный выбор по решению 75. Если выбранный экземпляр не удалось разместить в выбранном блоке, текущая попытка комнаты расходуется без перехода к обычной комнате. Решение 8 сохраняет возможность нескольких экземпляров и повторов; вес новой категории — 10, что даёт долю `10/110` на обычном этаже при суммарном весе прежних категорий 100 по решению 78а. Для `tiny_level` действует решение 79, для разрушенных этажей — запрет решения 80.

18. **Временная защита при генерации.** Постоянный `CAVE_ICKY` на клетках шаблона комнаты не устанавливается. Пока этаж достраивается, форма шаблона комнаты защищается временной маской генерации. Эта защита не ограничивает стандартных спутников основных монстров активной формой: после постановки всех основных монстров спутники могут появляться и в допустимых клетках за её пределами по решению 72. `CAVE_ICKY` сейчас помечает часть vault, а `CAVE_STCK` связан с запретом телепортации ([`defines.h`](src/common/defines.h#L5356), [`defines.h`](src/common/defines.h#L5368)).

19. **Профили монстров (пересмотрено для первой версии).** Позиция на карте монстров ссылается на профиль по символу этой карты; отдельного кода профиля нет по решению 62. Один профиль задаёт одно правило выбора: с полем `r_idx` выбирается точная базовая раса по решению 86; без него вид выбирается случайно среди кандидатов, прошедших указанные фильтры, правила данжа и глубины. Поля `flag`, `glyph`, `only_r_idx` и дополнительный диапазон базового уровня необязательны по решениям 87–90 и 98. Отбор уникальных задаётся `flag:UNIQUE`; без него сохраняется стандартный шанс, а `ego:required` и `ego:exact` неявно ограничивают выбор обычными по решениям 101 и 105. При `flag:UNIQUE` поле `ego` игнорируется по решению 106. Для точного `r_idx` уникальность определяется записью `r_info` и проверяется по указанным статическим фильтрам. Последовательных вариантов и произвольных запасных альтернатив нет. Отдельных полей `group`, `unique` и `exclude_r_idx` нет по решениям 98, 101 и 104; общий `flag` поддерживает настоящие именованные битовые флаги монстров всех семейств по решению 100. Заданные требуемые флаги соединяются по И без отрицания по решениям 95–96. Формат строк профиля определён решением 62; режимы эго — решением 24, обычная замена уникального — решением 107.

20. **Тематический пул монстров данжа (пересмотрен эффект запрета).** Профиль не подбирает монстра в обход обычного тематического пула данжа. Если правило профиля не даёт допустимого этим пулом монстра, соответствующая клетка остаётся пустой; экземпляр шаблона комнаты всё же может быть размещён.

20а. **Прежние альтернативы (пересмотрено для первой версии).** Последовательные варианты и произвольный запасной вариант из первоначального решения не используются. Кандидат единственного правила профиля должен пройти тематический пул данжа и ограничение глубины из решения 21; при отсутствии допустимого кандидата пропускается монстр, а не шаблон комнаты. Единственная встроенная обычная замена при неудаче с уникальным согласована с `flag:UNIQUE` решением 107.

21. **Глубина монстров.** Базовый уровень кандидата `r_info[r_idx].level` не должен превышать фактическую глубину текущего этажа. Это строгое правило действует для шаблонов комнат, даже если обычная генерация изредка допускает монстров выше уровня этажа (OoD). Разрешённая глубина самого шаблона его не отменяет. Если после отсева кандидатов не осталось допустимого монстра, его клетка остаётся пустой по решению 5. Уровень после применения эго отдельно не ограничивается по решению 67.

22. **Вес подходящих монстров.** Среди видов монстров, подходящих по условиям профиля, выбор учитывает их обычную редкость. Дополнительный сдвиг в пользу более сильных видов не вводится; дополнительный диапазон базового уровня может быть задан профилем по решению 88, но не обязателен. Без `flag:UNIQUE` сохраняется стандартный шанс уникального по решению 105, если `ego:required` либо `ego:exact` не ограничивают выбор обычными. Фильтры профиля, данжа и глубины продолжают действовать.

23. **Фильтры видов монстров (уточнено решениями 90–107).** Профиль может отбирать виды по общему полю `flag`, одному игровому символу `glyph`, включающему списку `only_r_idx` и диапазону `level`; каждый фильтр необязателен. Отдельных `group` и `exclude_r_idx` нет по решениям 98 и 104. Повторяемые строки `flag` принимают настоящие именованные битовые флаги монстров всех семейств по решению 100; псевдоимена и заглушки исключены. Несколько требуемых флагов соединяются по И между собой и с остальными фильтрами по решению 95; фильтра отсутствия флага нет по решению 96. Отсутствие всех видовых полей и `r_idx` допустимо по решению 87. Игровой символ — `r_info[r_idx].d_char` из записи `G:` в `r_info.txt`, а не символ карты шаблона комнаты ([`types.h`](src/common/types.h#L450), [`r_info.txt`](lib/game/r_info.txt)). Цвет при сравнении не учитывается, регистр учитывается. На профиль допускается ровно одна строка `glyph` с одним игровым символом; повторные строки и перечень символов не поддерживаются по решению 91. `only_r_idx` задаётся повторяемыми строками по одному числовому ID согласно решению 92 в части, сохранённой решением 104. Один игровой символ может соответствовать разным типам монстров: например, `glyph=s` не означает только скелетов. Точный `r_idx` нельзя сочетать с `only_r_idx` по решению 94. При обычной замене уникального `only_r_idx` игнорируется, `flag:UNIQUE` тоже игнорируется, остальные фильтры сохраняются по решению 107.

24. **Эго монстра.** Правило профиля поддерживает четыре режима: `none` — без эго; `auto` — обычный шанс получить совместимое эго; `required` — обязательная попытка выбрать любое совместимое эго без начального общего броска `MEGO_CHANCE`; `exact` — попытка применить конкретное эго без обычного броска шанса и редкости. Режим по умолчанию — `auto`. Уникальному монстру эго не назначается. Без `flag:UNIQUE` режимы `ego:required` и `ego:exact` неявно отбирают только обычные базовые расы по решению 105. При явном `flag:UNIQUE` это поле имеет приоритет: `ego` полностью игнорируется и для попытки уникального, и при обычной замене по решению 106. Если эго в `required` или `exact` выбрать либо применить не удалось к допустимой обычной базовой расе, монстр без эго создаётся в той же клетке по решениям 68–69; монстр пропускается только при невозможности выбрать, создать или поставить саму базовую расу по решению 5. Для точного уникального `r_idx` без `flag:UNIQUE` сочетание с `ego:required`/`ego:exact` статически несовместимо с неявным отбором обычных по решению 105; при наличии `flag:UNIQUE` эго игнорируется. После применения эго дополнительной жёсткой проверки уровня монстра нет по решению 67.

25. **Повтор профиля на карте монстров.** Если несколько клеток карты монстров содержат один и тот же символ профиля, выбор выполняется независимо для каждой позиции. Позиции монстров фиксированы шаблоном, а выбранные виды могут различаться. Уже выбранный и поставленный уникальный монстр повторно не выбирается; обычные ограничения уникальности сохраняются.

26. **Раздельный формат рельефа и сущностей.** Карта terrain отвечает только за рельеф; её символы не задают монстров и предметы и не ссылаются на их профили. Вместо ранее предложенного текстового списка координат используются отдельные карты монстров и предметов с теми же координатами. В каждой клетке карты допускается не более одной метки основного монстра и не более одной метки предмета; монстр и предмет могут быть заданы и поставлены в одной клетке. После нанесения рельефа сначала ставятся предметы, затем все основные монстры, после них группы или эскорты по решению 73. Неудача предмета не отменяет попытку монстра в той же клетке и наоборот. Позиции на картах сущностей ссылаются на соответствующие профили по символам. Выбор предметов и его необязательная постановка определены решением 40. Маркеры карт определены решениями 61 и 62.

27. **Редактор.** В будущую реализацию входит редактор шаблонов комнат в виде веб-страницы, работающий с принятой структурой шаблона и тремя картами. Проверка и показ ошибок определены решениями 56 и 151; локальный способ работы первой версии — решением 57. Редактор всегда находится в полном репозитории по ответу на Q144; загрузка игровых справочников определена решением 144а. Детали интерфейса определены решениями 145–153 ниже.

28. **Сущности и прозрачные клетки.** Заполненные позиции карт монстров и предметов допускаются только над активными (непрозрачными) клетками terrain-карты шаблона. Сущность над прозрачной клеткой считается ошибкой валидации шаблона. Прозрачные клетки не меняют исходный уровень, в том числе не получают монстров и предметы из шаблона. Кроме того, сущность над активной клеткой, где её постановка заведомо невозможна, отклоняется при загрузке по решению 74.

29. **Координаты входов.** Входы указываются отдельным списком координат, а не символами одной из трёх карт. Каждая координата входа должна указывать на активную проходимую клетку шаблона; недопустимая координата считается ошибкой валидации. Повтор той же координаты игнорируется по решению 143. При повороте или отражении шаблона координаты входов преобразуются вместе с картами. Для соединения с остальным уровнем действуют решения 3 и 12: при наличии входов достаточно соединить один, при их отсутствии соединение не требуется. Размещение списка в файле определено решением 31, система координат — решением 60.

30. **Структура шаблона.** Принято предложенное направление формата: название; размеры карты; профиль шаблона комнаты (в том числе отдельный символьный код по решению 32, ограничения глубины и список координат входов по решению 31); виды terrain; профили предметов; профили монстров; карта terrain; карта монстров; карта предметов. Настройки допустимых ориентаций нет по решению 85. Профили предметов входят в формат и могут использоваться несколькими позициями карты предметов. Три отдельные карты заменяют текстовые координатные записи из первоначального предложения в решении 26. Строки заголовка определены решением 58; директивы профиля шаблона комнаты и входов — решением 59; terrain — решением 61; монстров и предметов — решением 62. Допустимые поля профилей закрыты решениями 111, 135 и 138.

31. **Размещение входов в формате.** Отдельный список координат входов находится внутри раздела «профиль шаблона комнаты», рядом с ограничениями глубины. Каждая координата записывается повторяемой директивой `E:x:y` по решению 59; отдельной карты входов нет. Требования к координатам, преобразованию при всех восьми поворотах и отражениях и соединению с уровнем остаются определёнными решениями 29, 3, 12 и 85.

32. **Символьный код шаблона комнаты.** В описании каждого шаблона комнаты задаётся отдельный символьный код, отличный от отображаемого названия. По коду строки `I:+:<код>` и `I:-:<код>` из `d_info.txt` ссылаются на конкретные шаблоны комнат по решениям 15 и 82; переименование шаблона комнаты не меняет эти ссылки. Код должен быть уникальным в каталоге шаблонов комнат, что проверяется при валидации. Имя файла строится по коду согласно решению 52; допустимый формат кода определён решением 53.

33. **Размещение файлов.** Каждый шаблон комнаты хранится в отдельном файле в специально выделенной папке внутри `lib/game`. Уникальность символьных кодов проверяется среди всех загруженных шаблонов комнат согласно решению 32. Точный путь, расширение и связь имени файла с кодом определены решением 52.

34. **Формат файла.** Шаблон хранится в человекочитаемом текстовом формате с секциями в стиле `v_info.txt` и других файлов данных из `lib/game`. Формат должен представлять профиль шаблона комнаты, виды terrain, профили предметов и монстров и три отдельные карты согласно решению 30. Общие правила строк, комментариев, версии и порядка секций определены решением 54; утверждённые директивы перечислены в решениях 58–62, допустимые поля профилей — в решениях 111, 135 и 138. Обозначение пустых клеток определено решением 35.

35. **Пустая клетка карт.** Видимый символ `_` зарезервирован во всех трёх картах. В карте terrain он означает прозрачную клетку: при нанесении шаблона исходная клетка уровня остаётся без изменений. В картах монстров и предметов `_` означает отсутствие соответствующей сущности в этой координате. Каждая строка каждой карты должна иметь ровно заявленную ширину; один символ соответствует одной клетке. Будущая реализация должна явно отражать и обеспечивать это правило в коде разбора, валидации и нанесения шаблона. В комментарном заголовке каждого файла описания шаблона комнаты нужно объяснять значение `_` для всех трёх карт.

36. **Символы описаний и карт.** Каждое описание вида terrain, профиля предмета и профиля монстра резервирует текстовый символ. На соответствующей карте этот символ ссылается на данное описание. Пространства символов трёх слоёв независимы: один и тот же знак может одновременно обозначать вид terrain, профиль предмета и профиль монстра. В пределах одного слоя каждый непустой символ должен однозначно указывать на одно описание; два отдельных описания под одним символом считаются ошибкой валидации. Повторяемые строки `M` или `I` с разными полями одного символа дополняют одно описание по решению 62, а не резервируют символ повторно. Символ `_` нельзя резервировать для описаний, поскольку его значение уже определено решением 35. Допустимый набор символов определён решением 55.

37. **Идентификатор вида terrain.** Каждое описание вида terrain связывает зарезервированный им символ карты с числовым `f_idx` из `lib/game/f_info.txt`. Имя и экранный символ вида не используются как ключ: они могут повторяться. Веб-редактор сохраняет числовой `f_idx`, а при выборе показывает его вместе с именем, экранным символом и цветом вида; при необходимости также показывает флаги. Допустимость вида terrain определяется решением 38, синтаксис его описания — решением 61.

38. **Допустимые виды terrain в первой версии.** Шаблон может задавать только клетки, которые полностью и корректно создаются одним `f_idx` без дополнительных данных и специальных действий генератора. Проверка шаблона отклоняет наполненные фонтаны (`CS_FOUNTAIN`), ловушки, включая ловушки на дверях (`CS_TRAPS`), тайные двери с маскировкой (`CS_MIMIC`), парные порталы (`CS_BETWEEN`), магазины и двери домов с привязками к владельцу или доступу. Лестницы также запрещены: даже без обязательной записи `CS_*` их создание требует проверки контекста этажа. Обычные двери без ловушек и другой самодостаточный terrain допустимы. Постоянные клетки запрещены исходным требованием независимо от наличия дополнительных данных. Валидация должна явно проверять запрещённые специальные и контекстные виды; нельзя считать, что все они определяются одним общим флагом. Допустимый сам по себе `f_idx` дополнительно проверяется в каждой клетке с меткой монстра или предмета по решению 74.

39. **Преобразование terrain правилами этажа.** В первой версии до нанесения шаблона проверяются все его активные клетки с учётом выбранных позиции и ориентации. Если при установке заданного `f_idx` хотя бы одна клетка была бы заменена правилами этажа на другой вид terrain, эта ориентация на выбранном блоке отклоняется без изменения карты. Генератор может проверить следующую из восьми ориентаций того же шаблона на том же блоке по решениям 76 и 85; другой блок или шаблон возможен лишь в следующей попытке комнаты. Это касается, в частности, превращения дерева или куста над существующей лавой либо сильным огнём в мёртвое дерево, обычных покрытий и воды в `FEAT_NETHER_MIST` в Nether Realm, а также обычных покрытий и мелкой воды в `FEAT_DEEP_WATER` на этажах с `LF1_DEEP_WATER` ([`cave.c`](src/server/cave.c#L8895)). Прямой записью `f_idx` обходить эти правила нельзя. Прозрачные клетки не устанавливаются и сохраняют исходное состояние уровня; они не являются причиной отклонения по этому правилу.

40. **Профили и постановка предметов (пересмотрено для первой версии).** Каждый профиль предмета содержит одно правило: оно задаёт либо точный базовый вид через совместные `tval` и `sval`, либо случайный вид с необязательными фильтрами `tval` и базового уровня по решениям 112–113. Для случайного вида дополнительно поддерживаются необязательные фильтры по флагам предмета и игровому символу по решениям 117 и 124–125; с точным видом эти фильтры запрещены решением 126. Пустой профиль допустим по решению 116. Последовательных вариантов и запасных альтернатив нет. После нанесения terrain предметы ставятся первыми, строго в заданных клетках и без `drop_near` по решению 73. Если предмет нельзя выбрать, создать или поставить в указанную клетку, он в этой клетке отсутствует; экземпляр шаблона комнаты и последующая попытка основного монстра в этой же клетке сохраняются. Неудача монстра также не отменяет уже поставленный предмет. Переносить предмет в соседнюю клетку нельзя. Качество определено решениями 41 и 114; обычная случайная генерация артефактов — решением 43; режимы эго — решениями 44 и 115; случайный выбор базового вида — решением 49.

41. **Качество предмета.** Правило профиля предмета поддерживает режимы `normal`, `good` и `great`; по умолчанию используется `normal`. Текстовая форма `I:<символ>:quality:<режим>` определена решением 114. При случайном выборе режим влияет на отбор базового вида и создаваемые свойства. При точном `tval` и `sval` базовый вид остаётся заданным, а режим влияет на создаваемые свойства. Режим `verygreat` в первой версии не добавляется.

42. **Шанс появления предмета.** В первой версии профиль предмета не содержит отдельного поля вероятности появления. Каждая непустая клетка карты предметов всегда запускает попытку выбрать, создать и поставить предмет строго в эту клетку. Если попытка не удалась, предмет отсутствует, а шаблон комнаты сохраняется согласно решению 40.

43. **Случайные артефакты.** При стандартном создании предмета по профилю шаблона комнаты обычная случайная генерация истинных и случайных артефактов не отключается. Применяются стандартные ограничения игры и данжа, в том числе доступность и уникальность. Особые артефакты также проходят применимые фильтры профиля и жёсткий предел фактической глубины этажа по решению 121; обычный шанс допустимого артефакта сохраняется. Профиль не гарантирует конкретный истинный артефакт и не обходит эти ограничения. Для режима `required` сохранение артефактного шанса отдельно подтверждено решением 46; исключение для `exact` определено уточнением 46б. Техническое следствие решений 40 и 43: если уже созданный артефакт не удалось поставить точно в указанную клетку, предмет отсутствует, а состояние генерации артефактов не должно сохранять побочные эффекты от неразмещённого предмета.

44. **Эго предмета.** Профиль предмета поддерживает режимы `default` (стандартное поведение игры), `required` (совместимое эго обязательно, если не выпал допустимый артефакт, согласно уточнению 46а) и `exact` (задаются конкретные эго, до двух для одного предмета). Отдельных режимов `none` и `auto` нет. Режим `default` сохраняет обычную случайную генерацию артефактов согласно решению 43. `exact(id1)` означает ровно одно заданное эго, `exact(id1,id2)` — ровно два заданных эго; текстовая запись с числовыми ID из `e_info` определена решением 115.

    **Технические следствия для реализации решения 44.** Игровой объект хранит идентификаторы эго в `name2` и `name2b`; обычная генерация иногда назначает два эго ([`types.h`](src/common/types.h#L742), [`object2.c`](src/server/object2.c#L4922)). Для `exact` эго нужно выбрать и проверить **до** расчёта свойств, а не записывать готовому предмету после `apply_magic()`. Проверка должна учитывать существование идентификаторов в `e_info`, совместимость каждого эго с `tval/sval`, отсутствие повторного идентификатора, ограничения `ETR1_NO_DOUBLE_EGO` и `TR6_INSTA_EGO`, совместимость пары по признаку `before/after` и остальные действующие запреты сочетаний ([`object2.c`](src/server/object2.c#L5051)). Артефакт и эго не сосуществуют. Для `required` нельзя отключать обычный артефактный шанс по решению 46; если артефакт выпал, эго ему не требуется согласно уточнению 46а. Для `exact` артефактный бросок отключён согласно уточнению 46б. Правило уровня и редкости для `exact` определено решением 47.

45. **Количество предметов в позиции.** Каждая непустая клетка карты предметов создаёт один игровой объект. Для боеприпасов и расходников этот объект может быть стопкой. В первой версии профиль не задаёт размер стопки: используется стандартное количество, которое игра генерирует для выбранного вида предмета.

46. **Артефактный шанс в режиме `required`.** Режим эго предмета `required` сохраняет обычный шанс генерации истинного или случайного артефакта; сам режим не подавляет артефактный бросок. Для `default` действует стандартное поведение из решения 43. Результат выпадения артефакта определён уточнением 46а, поведение `exact` — уточнением 46б.

46а. **Результат выбора в режиме `required` (пересмотрен исход неудачи).** Сначала сохраняется обычный шанс получить допустимый артефакт; если он выпал, это успешный предмет и эго не требуется. Если артефакт не выпал, обязательно нужно выбрать совместимое эго. Если не удалось создать ни допустимый артефакт, ни предмет с совместимым эго, предмет отсутствует, а шаблон комнаты остаётся согласно решению 40. Точный базовый вид не отвергается при загрузке только из-за отсутствия совместимых эго по решению 132: допустимый артефакт всё ещё может появиться. Запасной альтернативы в первой версии нет.

46б. **Артефактный шанс в режиме `exact` (пересмотрен исход неудачи).** Для `exact(id1)` и `exact(id1,id2)` артефактный бросок отключён: предмет должен получить ровно одно или два указанных эго соответственно. Статическая несовместимость с точно указанным `tval`/`sval` — ошибка файла по решению 122. Если при случайном выборе базового вида заданное эго или пара несовместимы с выбранным видом либо предмет с ними нельзя корректно создать, предмет отсутствует, а шаблон комнаты остаётся согласно решению 40. Запасной альтернативы в первой версии нет.

47. **Уровень и редкость эго предмета.** Для `exact(id1)` и `exact(id1,id2)` не выполняется случайный бросок редкости каждого указанного эго. Наряду с проверками совместимости из решения 44 для каждого заданного эго требуется `e_info[e_idx].level` не выше фактической глубины этажа ([`types.h`](src/common/types.h#L325)). Если хотя бы одно эго не проходит проверку, предмет отсутствует, а шаблон комнаты остаётся по решению 40. Для `default` и `required` сохраняются обычные вероятностные правила генерации эго; артефактный бросок в `required` действует по уточнению 46а.

48. **Глубина базового вида предмета.** При точном выборе через `tval` и `sval` и при случайном выборе кандидат допускается только если базовый уровень вида `k_info[k_idx].level` не превышает фактическую глубину этажа ([`types.h`](src/common/types.h#L218)). Дополнительный включённый диапазон базового уровня профиля записывается `I:<символ>:level:<min>:<max>` по решению 113 только для случайного вида; он не отменяет жёсткий предел глубины этажа. Базовый вид выше уровня этажа (OoD) не должен попасть в итоговый предмет шаблона комнаты. Сочетание точного `tval`/`sval` с полем `level` — ошибка файла по пересмотру в решении 126; динамическое несоответствие фактической глубине пропускает предмет по решению 40. Применение жёсткого предела при случайном выборе уточнено решением 49.

49. **Случайный выбор базового вида предмета.** Для случайного выбора базового вида использовать `get_obj_num()` с фильтрами профиля и требованием качества из решения 41. До вызова исключить из доступных ему кандидатов все виды, у которых `k_info[k_idx].level` выше фактической глубины этажа согласно решению 48. Обычный механизм выбора лучшего из нескольких вариантов внутри `get_obj_num()` действует среди оставшихся кандидатов; тематическое взвешивание определено решением 50. Если после фильтрации вид выбрать нельзя, предмет пропускается по решению 40.

50. **Тематическое взвешивание предметов.** При случайном выборе базового вида через `get_obj_num()` применяется обычная `default_obj_theme` для весов категорий. Если базовый вид указан точно через `tval` и `sval`, тематическое взвешивание не требуется: выбранный вид не меняется, и тематические веса не служат жёстким запретом. Ограничение глубины из решения 48 и общие жёсткие ограничения из решения 51 действуют в обоих случаях.

51. **Общие ограничения генерации предметов.** Действующие жёсткие правила доступности предметов в игре и данже применяются как к случайному, так и к точно указанному базовому виду. Это включает, например, `WINNERS_ONLY` и ограничения на артефакты. Если точный вид запрещён, предмет пропускается без отмены шаблона комнаты по решению 40. Тематическое взвешивание `default_obj_theme` из решения 50 не является таким запретом для точного `tval` и `sval`.

52. **Каталог и имена файлов.** Все файлы шаблонов комнат хранятся в отдельном каталоге `lib/game/room_templates/`, по одному файлу `<code>.txt` на шаблон комнаты. Уникальный символьный `code` внутри описания обязан совпадать с частью имени файла перед `.txt`; несовпадение считается ошибкой загрузки. Настройки данжа ссылаются на `code`, а не на отображаемое название шаблона комнаты.

53. **Формат кода.** `code` шаблона комнаты и соответствующее имя файла используют `lower_snake_case`: код должен целиком соответствовать регулярному выражению `[a-z][a-z0-9_]*` и содержать не более 63 символов. Например, `orc_camp` и `dragon_nest_2`. Проверка формата применяется к внутреннему коду и имени файла по правилу решения 52.

54. **Основной синтаксис файла.** Файл использует строки вида `КОД:поля` в стиле `v_info.txt` и обязательно содержит строку версии `V:1`. Строки комментариев с `#` допустимы вне блоков карт. Определения видов terrain и профилей предметов и монстров идут до карт. У каждой из трёх карт — terrain, монстров и предметов — собственный маркер начала и ровно `h` строк по объявленной высоте шаблона; каждая строка имеет ровно объявленную ширину по решению 35. Внутри блоков карт строки трактуются как данные, без комментариев; пустые клетки обозначаются `_`, пробелы для их обозначения не используются. Заголовок определён решением 58, профиль шаблона комнаты и входы — решением 59, terrain — решением 61, профили и карты сущностей — решением 62.

55. **Символы карт и кодировка текста.** В трёх картах один символ клетки — один байт печатного ASCII в диапазоне `0x21..0x7E`, за исключением `:` и пробела; `_` отдельно зарезервирован для пустой клетки по решению 35 и не может быть символом описания. Таким образом, описание terrain, предмета или монстра может резервировать любой другой допустимый ASCII-символ. `#` внутри ровно `h` строк карты является обычным символом клетки, а не началом комментария; строки комментариев с `#` распознаются только вне блоков карт по решению 54. Названия и описания допускают UTF-8.

56. **Проверка файлов и сообщения об ошибках.** При запуске сервер проверяет все файлы шаблонов комнат. Ошибка обязательного поля, символа, размера карты, ссылки или любого другого правила формата и допустимости должна содержать путь файла, номер строки и причину; при такой ошибке запуск сервера прерывается. Сюда входят удалённые поля `unique` и `exclude_r_idx` по решениям 101 и 104; повтор одного `flag` либо любого одиночного поля `r_idx`, `glyph`, `level`, `ego` в профиле монстра по решению 102; несуществующий `re_idx` для `ego:exact` монстра по решению 89; неизвестный или повторный ID внутри `only_r_idx` по решению 92; неизвестное или неоднозначное имя флага, псевдоимя либо заглушка в `flag` монстра по решению 100; противоречие точного `r_idx` с `flag`, `glyph` или статическим диапазоном `level` и его сочетание с `only_r_idx` по решениям 94 и 97; точный уникальный `r_idx` с `ego:required`/`ego:exact` без `flag:UNIQUE` по решению 108; пустое по статическим фильтрам множество базовых рас случайного профиля, включая отсутствие уникальных при `flag:UNIQUE`, по решениям 103 и 109; `sval` предмета без `tval` по решению 112; повтор одиночных полей предмета `tval`, `sval`, `level`, `quality`, `ego` по решению 118; несуществующий точный `tval`/`sval`, обратный диапазон `level` или неизвестный режим `quality`/`ego` по решению 119; статически пустой набор базовых видов случайного профиля предмета по решению 120 или отсутствие среди них хотя бы одного совместимого с `ego:exact` вида по решению 134; неизвестный или повторный `e_idx` в точной паре эго предмета либо её статическая несовместимость с точным `tval`/`sval` по решению 122; запрещённое сочетание точного `tval`/`sval` с `flag`, `glyph` либо `level` по решению 126; повтор имени предметного `flag` по решению 124; неизвестный, неоднозначный либо запрещённый предметный флаг по решениям 127–128; повтор `glyph` или неверная длина его игрового символа по решению 129; а также статически невозможное размещение метки сущности на terrain по решению 74. Веб-редактор применяет те же правила, показывает ошибки по мере редактирования и разрешает экспорт игрового `.txt` только после их устранения по решению 151; черновик `.json` можно сохранить и при ошибках.

57. **Первая версия веб-редактора.** Редактор размещается как отдельная локальная страница в `tools/room_template_editor/` и работает без сети (offline), серверного компонента и логина. Браузер импортирует файл шаблона комнаты `.txt` или черновик `.json`, позволяет редактировать три слоя карт и профили, проверяет шаблон по решениям 56 и 151, скачивает черновик `.json` независимо от ошибок и экспортирует итоговый игровой `.txt` только после успешной проверки. Прямую запись в `lib/game/room_templates/` в первой версии не требуется.

58. **Заголовок файла шаблона комнаты.** В начале описания используются обязательные строки `V:1`, `N:<code>:<отображаемое имя>` и `S:<width>:<height>`. Поле `<code>` соответствует решениям 52–53; отображаемое имя может содержать UTF-8, размеры задают ширину и высоту всех трёх карт. Предел размеров определён решением 141. Пример: `V:1`, `N:orc_camp:Лагерь орков`, `S:20:12`.

59. **Директивы профиля шаблона комнаты и входов.** Настройки профиля записываются отдельными строками `P:<key>:<value...>`. Для `depth` и `weight` приняты конкретные формы и значения по умолчанию из решения 84; их допустимые значения и повторы — по решениям 139–140. Необязательная настройка просто не указывается: позиционные пустые поля для неё не требуются. Каждый вход записывается отдельной повторяемой строкой `E:x:y` в разделе профиля шаблона комнаты; повтор одинаковой координаты обрабатывается по решению 143. `P:orient` и иного ключа для ограничения ориентаций в первой версии нет по решению 85. Иных ключей `P` в первой версии нет по решению 138.

60. **Система координат входов.** В `E:x:y` используются координаты исходной карты с нулевой индексацией: `(0,0)` — левый верхний угол, `x` растёт вправо, `y` — вниз. Веб-редактор показывает те же координаты. В каждой из восьми ориентаций решения 85 координаты входов преобразуются вместе с тремя картами.

61. **Определения и карта terrain.** Каждый вид рельефа задаётся строкой `T:<символ>:<f_idx>`, где `<символ>` резервируется в слое terrain по решению 36, а `<f_idx>` — числовой идентификатор из `f_info.txt` по решению 37. Маркер `DT:` начинает карту terrain; после него идут ровно `<height>` строк карты с шириной `<width>` по заголовку из решения 58. Например, `T:#:55` показывает форму записи; сам вид должен также пройти проверку допустимости из решения 38.

62а. **Встроенная альтернатива для уникального монстра (уточнено решением 107).** Произвольных запасных профилей нет. При неудаче поставить уникального монстра встроенная замена пытается выбрать обычного по всем заданным `flag`, **кроме `UNIQUE`**, а также по одному `glyph` и диапазону `level`; `only_r_idx` при замене игнорируется. Отдельного `exclude_r_idx` нет по решению 104. Для точного уникального `r_idx` заданные фильтры также определяют кандидатов обычной замены, но биологический вид из исходного уникального автоматически не выводится по решению 99. На кандидата продолжают действовать ограничения данжа и фактической глубины. Если его нельзя выбрать, создать или поставить точно в клетку, монстр отсутствует, шаблон комнаты остаётся по решению 5. При явном `flag:UNIQUE` поле `ego` игнорируется и в этой попытке по решению 106.

62. **Символы профилей монстров и предметов.** Отдельного кода профиля нет: его идентификатором внутри файла является символ соответствующей карты. Пустая строка `M:<символ>:` объявляет профиль монстра со всеми значениями по умолчанию по решению 110; любая строка с полем `M:<символ>:<поле>:<значение...>` тоже неявно объявляет этот символ. Например, `M:a:` задаёт профиль для клеток `a` в карте `DM:`, а `M:a:flag:DRAGON` объявляет тот же символ с фильтром; `a` здесь **символ шаблона**, а не игровой `r_info.d_char`. Исчерпывающий набор полей `M` определён решением 111. Пустой профиль предмета объявляется `I:<символ>:` по решению 116; строки `I:<символ>:<поле>:<значение...>`, например `I:a:quality:great`, тоже объявляют символ неявно. Формы полей предмета `tval`, `sval`, `level`, `quality`, `ego` определены решениями 112–115. Символы слоёв независимы по решению 36, поэтому `a` может обозначать разные профили в картах монстров и предметов. `DM:` начинает карту монстров, `DI:` — карту предметов; после каждого маркера идут ровно `<height>` строк шириной `<width>`. В первой версии нет последовательных вариантов и директив `MV`/`IV`; единственное встроенное исключение для уникального монстра описано в уточнении 62а.

63. **Целевая попытка выбрать уникального монстра (пересмотрено решениями 101 и 105–107).** Поля `unique:yes`, `unique:no` и `unique_chance` отсутствуют. Для отбора уникальных используется `flag:UNIQUE` как обычный требуемый флаг; при неудаче с уникальным действует обычная замена по решению 107. Без `flag:UNIQUE` сохраняется стандартный шанс уникального по решению 105, кроме неявного отбора обычных при `ego:required`/`ego:exact`. Для точного `r_idx` признак уникальности берётся из `r_info`.

64. **Настройка уникальности монстра (пересмотрено решениями 101 и 105).** Отдельного поля `unique` нет; прежние режимы `yes` и `no` удалены. `flag:UNIQUE` — положительный фильтр, требующий этот флаг у кандидата. Без него сохраняется стандартный шанс уникального; отдельного способа принудить обычного монстра в первой версии нет. Исключение: `ego:required` и `ego:exact` неявно отбирают только обычные базовые расы по решению 105. У точного `r_idx` признак уникальности определяется записью `r_info`; указанные `flag` и прочие статические фильтры проверяются по решениям 94 и 97. Специальный процент `unique_chance` не вводится.

65. **Связь уникальности и эго (пересмотрено решениями 105–106).** Отдельных режимов `unique:yes/no` нет. Если `flag:UNIQUE` не указан, `ego:required` и `ego:exact` неявно ограничивают базовую расу обычными монстрами по решению 105. Если `flag:UNIQUE` указан, он имеет приоритет: поле `ego` полностью игнорируется и при попытке уникального, и при обычной замене по решению 106. Точное уникальное `r_idx` с обязательным/точным эго без `flag:UNIQUE` — ошибка файла по решению 108.

66. **Точный вид и уникальность (пересмотрено решениями 101 и 105–108).** Для точного `r_idx` признак уникальности берётся из записи `r_info`; отдельного поля `unique` для сопоставления нет. Если указан `flag:UNIQUE` или другой `flag`, точный вид должен обладать им по решениям 94 и 97: обычный точный вид с `flag:UNIQUE` — статическая ошибка. Точный уникальный вид без `flag:UNIQUE` допустим, когда нет противоречащего режима эго; отсутствие флага само по себе не требует обычного монстра. Если с ним задан `ego:required` или `ego:exact` без `flag:UNIQUE`, файл ошибочен, поскольку эти режимы неявно требуют обычную базовую расу по решению 108. С `flag:UNIQUE` эго полностью игнорируется по решению 106. При неудаче с точным уникальным действует обычная замена по решению 107; `only_r_idx` с точным `r_idx` запрещён по решению 94.

67. **Глубина монстра после применения эго.** Строгое ограничение глубины из решения 21 применяется к **базовой расе**: `r_info[r_idx].level` не выше фактической глубины этажа. Для режимов эго `auto`, `required` и `exact` дополнительного жёсткого ограничения по уровню монстра после применения эго нет. Проверки совместимости сохраняются; вероятность и редкость эго обрабатываются согласно режиму, причём `exact` пропускает обычный бросок по решению 68. Отсутствие post-ego cap не позволяет выбрать базовую расу выше глубины этажа.

68. **Точное эго монстра и неудача его применения.** `ego:exact:<re_idx>` задаёт конкретное эго. Обычный шанс появления и бросок редкости этого эго не выполняются; совместимость с выбранной базовой расой проверяется через `mego_ok()`, без дополнительной границы по итоговому уровню монстра согласно решению 67. Если существующее эго не проходит проверку совместимости или не может быть применено к выбранной базовой расе, в указанной клетке создаётся **базовый монстр без эго**. Такой же исход при неудаче попытки эго в режиме `required` установлен решением 69. При невозможности поставить и самого базового монстра клетка остаётся пустой по решению 5. Несуществующий `re_idx` — ошибка файла при загрузке по решению 89; игровой fallback без эго к нему не применяется.

69. **Неудача эго в режиме `required`.** Режим `ego:required` всегда делает попытку назначить эго выбранной обычной базовой расе: начальный общий шанс `MEGO_CHANCE` не может отменить эту попытку. Выбор конкретного эго сохраняет обычные проверки совместимости, глубинное вероятностное правило и редкость; дополнительного жёсткого cap по уровню после эго нет по решению 67. Если совместимое эго не выбрано или не применилось, **базовый монстр без эго всё равно создаётся в указанной клетке**. Если базовую расу нельзя выбрать, создать или точно поставить, клетка остаётся пустой по решению 5. Название режима `required` сохранено по решению 70: оно описывает обязательность попытки, а не гарантирует итоговое эго.

70. **Название режима эго монстра.** Название `ego:required` для монстров сохраняется. Оно означает обязательную **попытку** выбрать эго с поведением при неудаче из решения 69; итоговый монстр может остаться без эго. Одноимённый режим для предметов продолжает действовать по ранее принятым решениям 44 и 46а; правило о базовом монстре без эго на предметы не переносится.

71. **Группы и эскорты монстров шаблона комнаты.** Карта монстров фиксирует позиции только **основных** монстров, заданных её непустыми клетками. Если стандартная постановка выбранного основного монстра создаёт группу или эскорт, эти дополнительные монстры разрешены и появляются по обычным правилам вокруг него. Число фактически созданных монстров не ограничивается числом непустых клеток карты монстров. Защита предписанных позиций основных монстров обеспечивается порядком из решений 72–73.

72. **Порядок постановки монстров и спутников.** После постановки предметов по решению 73 выбрать и поставить по заданным клеткам всех основных монстров из карты монстров. Лишь после завершения этой фазы создавать стандартные группы и эскорты для тех основных монстров, которые действительно появились. Если основной монстр отсутствует, его группа или эскорт не создаются. Спутники используют обычные правила допустимости клеток и могут появиться также вне активной формы шаблона комнаты. Поскольку остальные основные монстры уже стоят на своих клетках, спутники не могут занять их предписанные позиции.

73. **Общий порядок постановки содержимого.** После успешного нанесения terrain шаблона комнаты генератор сначала создаёт предметы карты **строго в их клетках, без `drop_near`**, затем всех основных монстров карты по их клеткам и только после этого стандартные группы и эскорты успешно поставленных основных монстров по решению 72. Монстр и предмет могут сосуществовать на одной координате. Динамическая неудача постановки предмета не отменяет попытку монстра на той же клетке; динамическая неудача монстра не удаляет предмет и не отменяет шаблон комнаты. Заведомо невозможные сочетания terrain с метками сущностей исключаются раньше, при загрузке по решению 74.

74. **Статическая проверка клеток с сущностями.** При загрузке файла каждая метка основного монстра и предмета проверяется вместе с активным terrain в той же координате. Если постановка соответствующей сущности на таком terrain заведомо невозможна независимо от конкретного этажа и результата выбора, файл отклоняется с диагностикой из решения 56; например, метка основного монстра на стене, не проходящей требования `cave_empty_bold`. Редактор должен показывать ту же ошибку. Если пригодность зависит от состояния конкретного этажа или выбранной сущности, это не ошибка файла: неудача во время генерации пропускает только соответствующего монстра или предмет по решениям 5 и 40, сохраняя шаблон комнаты.

75. **Попытки построения комнат и неудача размещения.** Сохраняются до `DUN_ROOMS = 50` попыток построения комнат. Шаблон комнаты является одним из исходов общего выбора типа **очень необычной комнаты** после двух проверок `rand_int(DUN_UNUSUAL) < dun_lev` по уточнению 77а; отдельного процентного броска на каждой попытке нет. Категория участвует в розыгрыше только при выполнении предварительной проверки решения 78а. Когда выбран исход «шаблон комнаты», допустимый шаблон выбирается по весу. Несколько экземпляров и повтор одного шаблона возможны без отдельного лимита. Если выбранный экземпляр не удалось разместить в выбранном блоке — например, отдельный аналог `room_alloc()` не нашёл место, — попытка комнаты расходуется **без перехода к построению обычной комнаты**, аналогично внутренней неудаче `build_type7()`/`build_type8()` для vault. Один блок и порядок проверки ориентаций внутри попытки определены решением 76.

76. **Блок и ориентации внутри одной попытки.** Для сработавшей попытки шаблона комнаты фиксируются **один случайный блок** уровня и **один выбранный шаблон** из прошедших предварительную проверку решения 78а. Восемь ориентаций по решению 85 перебираются в случайном порядке на том же блоке до первой пригодной, которая и размещается; если подходящей нет, проверяются все восемь. Предпроверка каждой ориентации не должна менять карту до успешного выбора по решению 39. Другой блок или шаблон в пределах этой попытки не выбирается. Если ни одна ориентация не подошла, попытка комнаты расходуется без построения обычной комнаты по решению 75.

77. **Частота по аналогии с vault (пересмотрено).** Ранее принятое предложение о новой настройке `ROOM_TEMPLATE_CHANCE` и независимом плоском проценте на каждой попытке отменено пользователем. Частота шаблонов комнат определяется аналогично vault внутри существующего механизма очень необычных комнат, зависящего от глубины и `cfg.dun_unusual`. Сохраняются до `DUN_ROOMS = 50` попыток комнат, выбор по весам среди допустимых шаблонов и отсутствие отдельного лимита на количество или повторы. Точное место выбора закреплено уточнением 77а; предварительная проверка доступности и вес категории определены решением 78а.

77а. **Место в общем выборе очень необычной комнаты.** На неразрушенном этаже шаблон комнаты становится дополнительным типом в существующем общем розыгрыше с vault, гнёздами и ямами **после двух проверок** `rand_int(DUN_UNUSUAL) < dun_lev`, если предварительная проверка решения 78а нашла подходящие шаблоны. Это касается и `tiny_level` по решению 79, но запрещённые там vault не становятся допустимыми от появления новой категории; разрушенные этажи исключены по решению 80. Частота входа в эту ветку зависит от глубины и существующего `cfg.dun_unusual`; отдельной глобальной настройки `ROOM_TEMPLATE_CHANCE` нет. После выбора категории конкретный допустимый шаблон комнаты выбирается по весам. Повторы разрешены, расход попытки при неудаче размещения действует по решению 75. Вес категории «шаблон комнаты» в общем выборе типов — 10 по решению 78а.

78. **Неизменность старого розыгрыша без допустимых шаблонов комнат.** Категория «шаблон комнаты» не добавляется в розыгрыш очень необычных комнат, если предварительная проверка решения 78а не нашла ни одного подходящего шаблона. В этом случае исходные шансы vault, гнёзд и ям остаются ровно такими, какими были до добавления категории.

78а. **Предварительная доступность и вес категории.** До добавления новой категории к розыгрышу проверяется наличие хотя бы одного шаблона, допущенного правилами текущего данжа из `d_info.txt` по решениям 15 и 82–83, подходящего по глубине и способного по габаритам поместиться на этаже хотя бы в одной из восьми ориентаций решения 85. Если таких шаблонов нет, исходный розыгрыш старых типов выполняется без каких-либо изменений. Если они есть, категории «шаблон комнаты» добавляется вес 10 к суммарному весу 100 старых типов на обычном этаже: после двух проверок глубины и `DUN_UNUSUAL` её доля составляет `10/110` (около 9%). Соотношение весов старых типов сохраняется, но их абсолютные шансы немного снижаются. На `tiny_level` та же доля `10/110` сохраняется специальным правилом 81: запрещённые там vault не открываются, а прежний выбор комнат занимает оставшиеся `100/110`. Предварительная проверка не гарантирует пригодность конкретного случайного блока: если выбранный шаблон не поместился в нём ни в одной из восьми ориентаций, попытка расходуется по решениям 75–76.

79. **Маленький этаж `tiny_level`.** Шаблоны комнат разрешены на неразрушенном `tiny_level`, если хотя бы одна из восьми ориентаций шаблона физически помещается на этом этаже и соблюдены ограничения данжа и глубины из решения 78а. Для входа в общий выбор очень необычных комнат применяются те же две проверки глубины через `DUN_UNUSUAL`; доля шаблона комнаты затем составляет `10/110` по решению 81. Запрещённые на `tiny_level` старые типы vault не становятся допустимыми. Если подходящих шаблонов комнат нет, существующая генерация `tiny_level` и шансы старых типов не меняются. Если подходящий шаблон есть, но не подходит выбранный блок, попытка расходуется по решениям 75–76. Разрушенный `tiny_level` исключён по решению 80.

80. **Разрушенные этажи.** В первой версии шаблоны комнат не выбираются на разрушенных этажах, аналогично текущим vault. Это явное исключение из исходного правила 1: наличие цикла комнат само по себе не делает такой этаж допустимым. В текущем коде ветка разрушенного этажа предшествует выбору необычных комнат, а последующий `destroy_level()` может изменить terrain и удалить поставленных монстров и предметы. Проверка разрушенности должна исключать новую категорию из розыгрыша, не меняя существующие исходы генерации такого этажа.

81. **Доля шаблонов комнат на `tiny_level`.** После двух проверок глубины новая категория занимает ровно `10/110` розыгрыша, как на обычном этаже. Оставшиеся `100/110` передаются прежнему выбору комнат для `tiny_level` с его исходными относительными шансами и ограничениями. Исключение запрещённых там vault не приводит к перенормировке и увеличению доли шаблонов комнат. Если подходящих шаблонов нет, дополнительный розыгрыш не выполняется и прежняя генерация остаётся без изменений по решению 78.

82. **Списки конкретных шаблонов комнат в данже.** В `d_info.txt` допускаются повторяемые строки `I:+:<код>` для списка разрешений и `I:-:<код>` для списка запретов. В описании одного данжа можно использовать только один из этих режимов; смешение `+` и `-` — ошибка загрузки. Каждый `<код>` должен ссылаться на существующий шаблон комнаты, иначе загрузка завершается ошибкой. Общий флаг `NO_ROOM_TEMPLATES` запрещает шаблоны комнат даже при наличии строк `I:+:<код>`. Символ `I:` здесь относится к формату `d_info.txt` и не смешивается с директивами профилей предметов внутри файла шаблона комнаты.

83. **Отсутствие условий по данжам в шаблонах первой версии.** Файл шаблона комнаты не содержит перечня допустимых или запрещённых данжей. Привязка конкретных шаблонов комнат к данжам выполняется только через `I:+:<код>` либо `I:-:<код>` в `d_info.txt`; общий `NO_ROOM_TEMPLATES` действует независимо и имеет приоритет. При отсутствии списка конкретных кодов в данже все шаблоны каталога могут участвовать при соблюдении их ограничений глубины, физических размеров и остальных общих правил этажа. Это уточняет и заменяет часть раннего решения 9 о собственных условиях шаблона по допустимым данжам; ограничения глубины и размера сохраняются.

84. **Глубина и вес шаблона (уточнено решениями 139–140).** Необязательная строка `P:depth:<min>:<max>` задаёт включённый диапазон по фактической глубине текущего этажа: обе границы подходят. Если строки нет, сам шаблон не ограничивает глубину. Необязательная строка `P:weight:<положительное целое>` задаёт относительный вес шаблона среди подходящих шаблонов после фильтрации данжа, глубины и размеров по решениям 17 и 78а. Если строки нет, вес равен `1`. Допустимый диапазон веса — 1–1000. Этот вес не меняет вес `10` категории «шаблон комнаты» в общем выборе очень необычной комнаты.

85. **Все ориентации доступны.** В первой версии для любого шаблона всегда доступны восемь преобразований карты: повороты на 0°, 90°, 180° и 270° без отражения и те же четыре поворота после одного отражения. Ни `P:orient`, ни другого поля для ограничения этого набора нет. При размещении ориентации перебираются в случайном порядке на одном выбранном блоке до первого пригодного варианта либо исчерпания всех восьми по решению 76; карты terrain, монстров и предметов, а также координаты входов преобразуются одинаково. Это заменяет часть раннего решения 10 о возможности автора ограничить набор ориентаций.

86. **Точный вид монстра.** Строка `M:<символ>:r_idx:<номер>`, например `M:a:r_idx:971`, задаёт точную базовую расу. Если поле `r_idx` отсутствует, вид выбирается случайно по заданным фильтрам и общим правилам данжа и глубины. Отдельного поля `mode` или строки для переключения точного и случайного выбора нет. Уникальность точного вида проверяется по решениям 64–66; его базовый уровень также должен пройти ограничение глубины из решения 21.

87. **Случайный монстр без видовых фильтров.** Профиль без `r_idx`, `flag`, `glyph` и `only_r_idx` допустим; полностью пустой профиль задаётся строкой `M:<символ>:` по решению 110. Его статический пул берётся из всех базовых рас `r_info`, затем применяются другие заданные поля и проверка решения 103. На конкретном этаже действуют ограничения данжа, фактической глубины и доступности уникальных. Без `flag:UNIQUE` сохраняется стандартный шанс уникального, кроме неявного отбора обычных при `ego:required`/`ego:exact` по решению 105. Если кандидаты исчезли только динамически, пропускается монстр в клетке по решению 5.

88. **Диапазон базового уровня монстра.** Необязательная строка `M:<символ>:level:<min>:<max>`, например `M:a:level:20:40`, задаёт включённые границы для `r_info[r_idx].level`. Она применяется к кандидату базовой расы, в том числе когда указан точный `r_idx`; статическое несоответствие точного вида диапазону — ошибка файла по решению 97. Если строки нет, дополнительного диапазона у профиля нет; жёсткий предел `r_info[r_idx].level ≤ фактическая глубина этажа` из решения 21 сохраняется. Уровень после эго отдельно не ограничивается по решению 67.

89. **Проверка точного эго монстра.** Если `M:<символ>:ego:exact:<re_idx>` ссылается на несуществующий `re_idx`, файл шаблона комнаты отклоняется при загрузке с диагностикой решения 56. Если `re_idx` существует, но это эго несовместимо с выбранной базовой расой или не применилось, монстр создаётся без эго по решению 68. Это не отменяет попытку поставить базового монстра и не отменяет генерацию шаблона комнаты.

90. **Флаги монстра вместо узкого видового `group` (уточнено решением 100).** Фильтрация монстров не ограничивается видовыми флагами `RF3`: допускаются настоящие именованные битовые флаги монстров всех семейств. Отдельное поле `group` не используется по решению 98; флаги задаются повторяемым общим полем `flag` по решению 100. Несколько требуемых флагов соединяются по И по решению 95; запретного фильтра нет по решению 96.

91. **Один игровой символ в фильтре `glyph`.** В одном профиле допускается не более одной строки `M:<символ>:glyph:<игровой символ>`, причём значение содержит ровно один игровой символ `r_info[r_idx].d_char`. Повторные строки `glyph` и списки нескольких символов не поддерживаются и являются ошибкой файла. Это заменяет прежнюю часть решения 23 о множестве символов с объединением по ИЛИ. Отсутствие строки оставляет этот фильтр выключенным.

92. **Список ID монстров (пересмотрено решением 104).** Список `only_r_idx` задаётся повторяемыми строками `M:<символ>:only_r_idx:<числовой ID>`, по одному ID в строке. Ссылка на несуществующий ID или повтор одного ID в списке — ошибка файла при загрузке по решению 56. Ранее из решения 23 здесь также был введён `exclude_r_idx` с аналогичным синтаксисом; пользователь исключил его из первой версии решением 104. `only_r_idx` игнорируется при обычной замене уникального по решению 107, а с точным `r_idx` несовместим по решению 94.

93. **Фильтры при обычной замене уникального (пересмотрено решениями 104 и 107).** Встроенная замена игнорирует только `flag:UNIQUE` и список `only_r_idx`; остальные заданные `flag` (все по И), один `glyph` и диапазон `level` сохраняются. Отдельного `exclude_r_idx` нет по решению 104. Видовой флаг не выводится из исходного уникального монстра по решению 99. Общие ограничения данжа и фактической глубины продолжают действовать.

94. **Фильтры при точном `r_idx`.** При загрузке файла точная раса из `M:<символ>:r_idx:<ID>` должна соответствовать всем указанным `flag`, единственному `glyph` и диапазону `level` по решению 97; несоответствие — ошибка файла. Точный `r_idx` нельзя сочетать с `only_r_idx`: такое сочетание тоже является ошибкой. `exclude_r_idx` удалён решением 104. Для точного уникального монстра заданные фильтры используются при обычной замене с исключением `flag:UNIQUE` по решению 107. Форма записи `flag` определена решением 100. Несоответствие глубине конкретного этажа обрабатывается динамически по решениям 21 и 97; сочетание точного уникального с эго — по решению 108.

95. **Сочетание требуемых флагов.** Если в профиле указано несколько требуемых флагов монстра через повторяемые строки `flag` из решения 100, кандидат должен обладать **каждым** из них: флаги соединяются по И. Это условие также соединяется по И с заданными `glyph`, включённым диапазоном `level` и списком `only_r_idx` с учётом правил решений 93–94. При обычной замене уникального `flag:UNIQUE` и `only_r_idx` исключаются по решению 107; остальные флаги продолжают соединяться по И. `exclude_r_idx` удалён решением 104. Имена флагов и область допустимых семейств определены решением 100.

96. **Без фильтра отсутствия флага.** В первой версии можно требовать наличие флага по решениям 90 и 95, но нельзя задать условие отсутствия или запрета конкретного флага. Не добавляется отдельное поле, префикс отрицания или иной эквивалент такого условия.

97. **Статическая и динамическая проверки точного монстра.** При загрузке файла точный `r_idx` должен соответствовать заданному диапазону базового уровня `level`, всем требуемым флагам и `glyph`. Любое статическое несоответствие делает файл ошибочным по решению 56. Если этот корректный профиль не проходит проверку **фактической глубины конкретного этажа** по решению 21, пропускается только монстр в данной клетке; файл остаётся корректным, генерация всего шаблона комнаты не отменяется по решению 5.

98. **Единый фильтр `flag`, без отдельного `group`.** В профиле монстра для отбора по флагам используется только общий фильтр `flag`; отдельного поля `group` в первой версии нет. Этот фильтр поддерживает настоящие именованные битовые флаги монстров всех семейств по решению 100, а не только видовые `RF3`. Правило И для нескольких требуемых флагов принято решением 95, отрицательные флаги не поддерживаются по решению 96. Флаг `UNIQUE` используется вместо удалённого `unique:yes` по решению 101. При обычной замене этот флаг исключается, остальные требуемые флаги сохраняются по решению 107; вид исходного уникального автоматически не выводится по решению 99.

99. **Обычная замена уникального без вывода вида (уточнено решением 107).** При неудаче поставить уникального применяется одна обычная замена по заданным `flag`, одному `glyph` и диапазону `level`; `flag:UNIQUE` и `only_r_idx` для неё игнорируются по решению 107. `exclude_r_idx` удалён решением 104. Видовой флаг из исходного уникального не выводится: чтобы требовать обычного дракона, автор явно указывает `M:<символ>:flag:DRAGON` по решению 100. Общие ограничения данжа и фактической глубины остаются обязательными.

100. **Запись флагов монстров.** Фильтр задаётся повторяемыми строками `M:<символ>:flag:<имя>`, по одному имени флага на строку. Имя записывается так, как в `r_info.txt`, **без** префикса семейства `RF1_`, `RF3_` и подобных; примеры — `M:a:flag:DRAGON` и `M:a:flag:RES_FIRE`. Допустимы только настоящие именованные битовые флаги монстров всех семейств. Псевдоимена `DUN_*`, `K_INFO_*`, `F_INFO_*`, заглушки `X...` и флаги предметов из `k_info` не относятся к этому набору и запрещены. Неизвестное или неоднозначное имя — ошибка файла при загрузке по решению 56. Несколько строк `flag` требуют наличия всех названных флагов по решению 95; отрицательных условий нет по решению 96. Это уточняет открытые части решений 90 и 98.

101. **Удаление специального поля уникальности (дополнено решениями 105–107).** Поля `M:<символ>:unique:yes` и `M:<символ>:unique:no` в первой версии нет. Вместо прежнего `unique:yes` автор указывает требуемый флаг `M:<символ>:flag:UNIQUE` из решения 100. Без него сохраняется стандартный шанс уникального; отдельного принудительного режима только обычных нет по решению 105, хотя `ego:required`/`ego:exact` неявно отбирают обычных. При `flag:UNIQUE` эго игнорируется и для уникальной попытки, и для обычной замены по решению 106. При замене удаляется только `UNIQUE` и игнорируется `only_r_idx`, остальные фильтры сохраняются по решению 107.

102. **Повторные поля профиля монстра.** Повтор одного и того же имени флага `M:<символ>:flag:<имя>` в одном профиле — ошибка файла; разные `flag` остаются повторяемыми по решению 100. Поля `r_idx`, `glyph`, `level` и `ego` допускаются не более одного раза на профиль: повтор любого из них — ошибка файла при загрузке. Поле `unique` удалено решением 101 и не входит в набор одиночных полей. Список `only_r_idx` остаётся повторяемым по решению 92, а `exclude_r_idx` полностью удалён решением 104.

103. **Статическая пустота случайного профиля.** При загрузке файла случайный профиль без `r_idx` проверяется по статическим фильтрам против всего `r_info`. Если ни одна базовая раса им не соответствует, файл ошибочен, с диагностикой из решения 56. Для `flag:UNIQUE` эта проверка обязана найти хотя бы одного подходящего уникального по решению 109; возможность обычной замены её не ослабляет. Если статически хотя бы одна раса подходит, но на конкретном этаже не осталось кандидата из-за тематики данжа, фактической глубины или текущей доступности уникальных, пропускается только монстр в указанной клетке по решению 5; файл и весь шаблон комнаты сохраняются после предусмотренной попытки замены по решению 107.

104. **Удаление `exclude_r_idx` из первой версии.** Поле `exclude_r_idx` полностью удалено из формата профиля монстра: оно не участвует ни в исходном выборе, ни в обычной замене уникального. Это пересматривает первоначальное добавление фильтра в решении 23, его синтаксис из решения 92 и упоминания в решениях 93–95 и 99. Список `only_r_idx` остаётся по решению 92; его игнорирование при обычной замене сохраняется по решению 107. Файл с `exclude_r_idx` отклоняется как содержащий неизвестное/удалённое поле по решению 56.

105. **Шанс уникального без `flag:UNIQUE`.** Отдельного поля `unique` нет. Если `flag:UNIQUE` не указан, действует стандартный шанс генерации уникального монстра среди подходящих кандидатов. Отдельного способа принудить выбор только обычного монстра в первой версии нет; при этом `ego:required` и `ego:exact` по прежнему неявно отбирают только обычные базовые расы. Эти правила уточняют открытые части решения 101 и не отменяют статические проверки фильтров и динамическую доступность уникальных.

106. **Приоритет `flag:UNIQUE` над эго.** Если в профиле явно задан требуемый `flag:UNIQUE`, поле `ego` полностью игнорируется независимо от записанного режима. Это относится и к попытке поставить уникального монстра, и к встроенной обычной замене при её неудаче. Без `flag:UNIQUE` режимы `ego:required` и `ego:exact` неявно выбирают только обычных по решению 105. Такое правило сохраняет ранее выбранный приоритет уникального над эго после удаления отдельного поля `unique`.

107. **Фильтры обычной замены после `flag:UNIQUE`.** Если уникального монстра не удалось поставить, при поиске обычной замены из набора требуемых флагов игнорируется **только `UNIQUE`**. Все прочие `flag` остаются и соединяются по И; единственный `glyph` и диапазон `level` сохраняются. Список `only_r_idx` игнорируется, чтобы он не запретил обычную замену. `exclude_r_idx` удалён решением 104 и нигде не применяется. Видовые флаги из исходного уникального автоматически не выводятся по решению 99; продолжают действовать ограничения данжа и глубины. При явном `flag:UNIQUE` поле `ego` игнорируется и в обычной замене по решению 106.

108. **Точный уникальный монстр и обязательное эго.** Точный уникальный `r_idx` вместе с `ego:required` или `ego:exact` **без** `flag:UNIQUE` — ошибка файла при загрузке: эти режимы эго по решению 105 неявно требуют обычную базовую расу. Если `flag:UNIQUE` указан и точный вид действительно уникален, `ego` игнорируется по решению 106. Точный обычный `r_idx` вместе с `flag:UNIQUE` — ошибка статического несоответствия флагу по решениям 94 и 97. Отсутствие `flag:UNIQUE` само по себе не делает точный уникальный `r_idx` ошибочным, если нет противоречащего режима эго.

109. **Статический кандидат для `flag:UNIQUE`.** Если профиль требует `flag:UNIQUE`, то при загрузке файла среди всех базовых рас `r_info` должен существовать хотя бы один уникальный монстр, удовлетворяющий всем остальным статическим фильтрам профиля (`flag`, `glyph`, `level`, `only_r_idx` там, где он допустим). Если такого уникального нет, файл ошибочен по решению 56, **даже если** поиск обычной замены без `UNIQUE` мог бы найти кандидата. Динамическая недоступность такого уникального в конкретном данже или на конкретной глубине обрабатывается во время генерации по решениям 103 и 107.

110. **Объявление пустого профиля монстра.** Строка `M:<символ>:` без поля объявляет профиль монстра с настройками по умолчанию. В частности, `M:a:` разрешает символ `a` на карте монстров после `DM:` и даёт неограниченный видовыми фильтрами случайный выбор по решению 87. Если для символа есть хотя бы одна строка `M:<символ>:<поле>:<значение...>`, она сама объявляет профиль и отдельная пустая строка не обязательна. `<символ>` — один допустимый символ слоя карты монстров по решениям 36 и 55, не отображаемый игровой символ монстра из `r_info`; символ того же вида может независимо использоваться в карте terrain или предметов.

111. **Закрытый набор полей профиля монстра первой версии.** После `M:<символ>:` допускаются ровно шесть полей: одиночное `r_idx`, повторяемое `flag` (разные имена по одному на строку), одиночное `glyph`, одиночное `level`, повторяемое `only_r_idx` и одиночное `ego`. Также допустима пустая строка `M:<символ>:` для профиля со значениями по умолчанию по решению 110. Полей `group`, `exclude_r_idx` и `unique` нет; другие поля `M` в первой версии не принимаются. Повтор и несовместимость полей проверяются по решениям 56, 92, 94 и 102. Значения и поведение этих шести полей определены соответствующими ранее принятыми решениями; набор полей профиля монстра считается закрытым.

112. **Вид предмета через `tval` и `sval`.** В профиле предмета используются отдельные строки `I:<символ>:tval:<число>` и `I:<символ>:sval:<число>`. Один `tval` без `sval` задаёт случайный выбор вида указанного типа. Совместные `tval` и `sval` задают точный базовый вид. Без обоих полей выбор базового вида случайный без ограничения по типу согласно решению 116. `sval` без `tval` — ошибка файла при загрузке. Отдельного поля `mode` для переключения точного и случайного выбора нет, внутренний `k_idx` в файле не указывается по решению 123. С точным видом нельзя указывать `flag`, `glyph` или `level` по решению 126. На оба способа продолжают действовать жёсткие ограничения глубины и доступности из решений 48 и 51.

113. **Дополнительный диапазон уровня предмета (пересмотрено решением 126).** Необязательная строка `I:<символ>:level:<min>:<max>` задаёт включённые границы для базового `k_info[k_idx].level` при случайном выборе вида. При её отсутствии дополнительного диапазона нет. С точной парой `tval`/`sval` строка `level` запрещена и вызывает ошибку загрузки даже при совпадении диапазона с уровнем точного вида. Это пересматривает прежнее правило о проверке соответствия точного вида диапазону. Независимо от поля `level` всегда действует жёсткий предел `k_info[k_idx].level ≤ фактическая глубина этажа` из решения 48; его несоблюдение на конкретном этаже динамически пропускает предмет без отмены шаблона комнаты по решению 40.

114. **Текстовая запись качества предмета.** Строка `I:<символ>:quality:normal|good|great` задаёт один из трёх режимов качества из решения 41. Если строка отсутствует, используется `normal`. В первой версии не вводится `verygreat`; влияние качества на случайный либо точный базовый вид остаётся тем, что определено решением 41.

115. **Текстовая запись эго предмета.** Строка `I:<символ>:ego:default` сохраняет стандартное поведение игры, `I:<символ>:ego:required` требует совместимого эго при отсутствии допустимого артефакта, `I:<символ>:ego:exact:<e_idx>` задаёт одно точное эго, а `I:<символ>:ego:exact:<e_idx1>:<e_idx2>` — ровно два. Идентификаторы числовые из `e_info`. Если строки `ego` нет, применяется `default`. Ранее принятые ограничения совместимости, артефактного шанса и глубины эго из решений 44, 46а, 46б и 47 сохраняются.

116. **Пустой профиль предмета.** Строка `I:<символ>:` объявляет профиль предмета без полей: базовый вид выбирается случайно без дополнительных фильтров `tval` и `level`, качество `normal`, режим эго `default`. Любая строка `I:<символ>:<поле>:<значение...>` тоже неявно объявляет символ; отдельная пустая строка тогда не обязательна. `<символ>` относится к слою карты предметов `DI:`, не к игровому символу предмета и не к символам других слоёв по решениям 36 и 62. Каждая клетка с ним всегда делает одну попытку постановки по решению 42; при неудаче предмет отсутствует, а шаблон комнаты сохраняется по решению 40.

117. **Дополнительные фильтры предмета (завершено решением 135).** Исходный набор из пяти полей `tval`, `sval`, `level`, `quality`, `ego` дополнен фильтрами по флагам предмета (`flag`) и по его игровому символу (`glyph`); исчерпывающий набор первой версии закреплён решением 135. Повторяемость и логика `flag` определены решениями 124–125, допустимые имена — решениями 127–128, игровой символ — решением 129. Поле внутреннего `k_idx` не используется по решению 123. `flag`, `glyph` и `level` допустимы только для случайного выбора вида по решению 126 и проверяются по базовому виду по решению 130.

118. **Повтор одиночных полей предмета (уточнено решениями 129 и 131).** Каждое из уже определённых полей `tval`, `sval`, `level`, `quality`, `ego` в одном профиле `I:<символ>` может встречаться не более одного раза. Повтор любого из них — ошибка файла при загрузке. `flag` повторяем с разными именами по решению 124; `glyph` одиночное, и его повтор ошибочен по решению 131.

119. **Ошибочные значения вида и режима предмета.** Несуществующая точная пара `tval`/`sval`, диапазон `level` с `min > max`, неизвестное значение `quality` или режима `ego` — ошибки файла при загрузке. Сочетание точного вида с `level` запрещено решением 126, поэтому прежняя проверка статического соответствия точного вида диапазону из решения 113 больше не применяется.

120. **Пустой набор кандидатов предмета (дополнено решением 134).** Если статические фильтры и требование качества случайного профиля не оставляют ни одного базового вида во всём каталоге предметов, файл ошибочен при загрузке. При `ego:exact` дополнительно нужен хотя бы один статически подходящий базовый вид, совместимый с указанным эго или парой, по решению 134. Если кандидаты исчезают только с учётом конкретного данжа, фактической глубины или другой динамической доступности, предмет в этой клетке пропускается без отмены шаблона комнаты по решению 40.

121. **Фильтры для особых артефактов (уточнено решениями 126 и 133).** Особый артефакт, появляющийся при обычном артефактном броске, обязан проходить применимые фильтры профиля: `tval` и, только при точном виде, `sval`; при случайном виде — `level`, `flag` и `glyph`, если они заданы, с проверкой флага и символа по базовому виду согласно решению 130. Жёсткий предел фактической глубины этажа действует всегда. При точном `tval`/`sval` поле `level` запрещено решением 126. Ранняя ветка `INSTA_ART` подчиняется тем же фильтрам до принятия или пометки артефакта по решению 133. Обычный шанс генерации допустимого артефакта сохраняется для режимов `default` и `required` по решениям 43 и 46; для `exact` артефактный бросок по прежнему отключён решением 46б.

122. **Проверка точного эго предмета (дополнено решением 134).** Несуществующий числовой `e_idx` или повтор одного `e_idx` внутри пары `exact:<e_idx1>:<e_idx2>` — ошибка файла при загрузке. Если точный базовый вид `tval`/`sval` статически несовместим с указанным `ego:exact`, файл ошибочен. Для случайного вида при загрузке требуется хотя бы один совместимый с указанным эго или парой вид среди статически подходящих кандидатов по решению 134. Если выбранный при генерации конкретный случайный вид несовместим, предмет пропускается без выбора замены и без отмены шаблона комнаты. Динамические ограничения эго на фактическом этаже продолжают действовать по решению 47.

123. **Без внутреннего `k_idx` в формате.** Поле `k_idx` и отдельный включающий список `only_k_idx` для предметов в первой версии не вводятся. Конкретный базовый вид задаётся парой `tval` и `sval` по решению 112; без этой пары вид выбирается случайно по применимым фильтрам. Это закрывает вопрос о роли `k_idx` из решения 117.

124. **Повторяемые требуемые флаги предмета (дополнено решением 127).** Каждая строка `I:<символ>:flag:<имя>` задаёт один требуемый флаг. Строки повторяемы для разных флагов; кандидат обязан иметь все перечисленные флаги одновременно (логическое И). Повтор одного и того же флага в одном профиле — ошибка файла. Допустимые имена и семейства флагов определены решениями 127–128.

125. **Без отрицательных флагов предмета.** В первой версии профиль предмета может требовать наличие флага по решению 124, но не может запрещать флаг или требовать его отсутствия. Отдельного отрицательного поля либо оператора нет.

126. **Точный вид без дополнительных видовых фильтров.** Если указаны и `tval`, и `sval`, поля `flag`, `glyph` и `level` в том же профиле запрещены; любое сочетание — ошибка файла при загрузке, даже если фильтр соответствует точно выбранному виду. Это пересматривает прежнее правило решения 113 о проверке соответствия точного вида диапазону `level`: теперь сам диапазон при точном виде недопустим. Жёсткий предел фактической глубины этажа из решения 48 остаётся обязательным. При случайном виде `flag`, `glyph` и `level` могут ограничивать выбор.

127. **Имена флагов предмета.** В строке `I:<символ>:flag:<имя>` имя записывается точно как именованный флаг в поле `F` файла `k_info.txt`, без программного префикса семейства. Разрешены настоящие именованные флаги из шести стандартных семейств флагов базового вида предмета и семейства ESP. Неизвестное либо неоднозначное имя, а также имена заглушек `XXX...` — ошибка файла при загрузке. Это касается предметных флагов базового `k_info`, а не одноимённых флагов монстров.

128. **Запрет алиасов ловушек.** Имена флагов ловушек, представляющие альтернативные значения тех же битов, в первой версии запрещены в `I:<символ>:flag:<имя>`: они могут пересекаться с обычными флагами предметов, например `ONLY_DRAGON` и `SUST_CON`. Используются только имена настоящих флагов базовых предметов из решения 127; алиас ловушки считается ошибкой файла.

129. **Игровой символ предмета.** Строка `I:<символ>:glyph:<один символ>` задаёт один игровой символ базового вида из записи `G` в `k_info.txt` (`k_char`); регистр учитывается. Это не символ слоя карты предметов `DI:` и не изменяемое отображение предмета в клиенте или у конкретного игрока. В одном профиле может быть только одна строка `glyph`; повтор — ошибка файла.

130. **Фильтры по базовому виду.** `flag` и `glyph` проверяются только по базовой записи `k_info` до назначения эго, артефакта и других изменений объекта. Получившиеся у готового предмета флаги и отображаемый символ повторно по этим фильтрам не проверяются. Проверка статически пустого набора кандидатов по решению 120 также опирается на базовые записи.

131. **Одна строка игрового символа предмета.** Поле `I:<символ>:glyph:<один символ>` одиночное в пределах одного профиля предмета. Повтор строки `glyph`, в том числе с тем же значением, — ошибка файла при загрузке. Это закрепляет ограничение из решения 129.

132. **Точный вид с `ego:required`.** При точных `tval`/`sval` и `ego:required` отсутствие совместимого эго само по себе не является ошибкой файла при загрузке: может выпасть допустимый артефакт по решениям 43 и 46а. На конкретном этаже, если не появился ни допустимый артефакт, ни совместимое эго, предмет в назначенной клетке пропускается без отмены шаблона комнаты. Проверки точного `ego:exact` из решения 122 этим не меняются.

133. **Ранний предложенный артефакт.** Ответ «используем предложенный» относится только к артефакту, который уже проходит профиль. В ранней ветке `INSTA_ART` предложенный артефакт до принятия и до изменения отметок его доступности проверяется по всем применимым фильтрам профиля из решения 121 и по жёсткому пределу фактической глубины этажа. При точном `tval`/`sval` артефакт другого базового вида не допускается и не подменяет точный предмет. Подходящий предложенный артефакт используется. Если ранний кандидат не подходит, его отклоняют без пометки; допускается продолжить обычную генерацию по профилю с обычным шансом допустимого артефакта. Это не нарушает решение 121.

134. **Статическая совместимость случайного вида с точным эго.** Если случайный профиль использует `ego:exact:<e_idx>` или `ego:exact:<e_idx1>:<e_idx2>`, после применения всех статических фильтров базового вида и требования качества среди кандидатов `k_info` должен оставаться хотя бы один вид, способный принять указанное эго или оба эго вместе. Если такого вида нет, файл отклоняется при загрузке по решению 56. Наличие хотя бы одного совместимого вида делает профиль допустимым, но не обязывает генератор выбирать именно его: при выборе конкретного несовместимого вида на этаже предмет пропускается по решению 122, без новой попытки и без отмены шаблона комнаты. Динамические ограничения данжа и глубины действуют отдельно.

135. **Закрытый набор полей профиля предмета первой версии.** После `I:<символ>:` допускаются ровно семь полей: одиночные `tval`, `sval`, `level`, `glyph`, `quality`, `ego` и повторяемое `flag` (по одному имени на строку, повтор одного имени ошибочен). Пустое объявление `I:<символ>:` допустимо и задаёт значения по умолчанию по решению 116. Внутреннего `k_idx`, списка `only_k_idx`, отрицательных флагов, отдельного шанса появления предмета и настройки размера стопки нет по решениям 42, 45, 123 и 125. Совместные `tval`/`sval` задают точный вид и запрещают `level`, `flag`, `glyph` по решениям 112 и 126; без `sval` вид выбирается случайно. Значения, проверки и постановка предмета определены решениями 40–51 и 112–134. Другие поля `I` в первой версии не принимаются; набор полей профиля предмета закрыт.

136. **Признак комнаты на активной форме.** Каждая активная клетка terrain получает `CAVE_ROOM` при нанесении шаблона комнаты. Отдельного переключателя `P:room` нет. Прозрачные клетки сохраняют все свои прежние свойства, в том числе имеющийся или отсутствующий `CAVE_ROOM`. Это дополняет правило 11.

137. **Освещение.** В первой версии нет поля `P:light`: к активным клеткам применяются обычные правила освещения этажа и свойства terrain. Прозрачные клетки шаблон комнаты не меняет, включая их освещение. Это дополняет правило 11.

138. **Закрытый набор полей профиля шаблона комнаты.** В первой версии допустимы только `P:depth:<min>:<max>` и `P:weight:<положительное целое>` по решению 84; оба поля необязательны. Отдельных `P:room`, `P:light`, `P:orient` и других ключей нет. Входы задаются повторяемыми строками `E:x:y`, а не полем `P`. Списки конкретных шаблонов комнат для данжа задаются в `d_info.txt` по решениям 82–83. Другие строки `P` являются ошибкой файла при загрузке.

139. **Границы глубины профиля.** Для `P:depth:<min>:<max>` допустимы целые значения `1 ≤ min ≤ max < MAX_DEPTH`; текущее `MAX_DEPTH` равно 255. Нарушение диапазона — ошибка файла при загрузке. Наличие сейчас настроенного данжа на хотя бы одной глубине указанного диапазона не требуется.

140. **Вес, повторы и суммирование.** Значение `P:weight` — целое число от `1` до `1000` включительно; остальные значения — ошибка файла. При выборе среди подходящих шаблонов сумму их весов считают с защитой от переполнения. Повтор `P:depth` или `P:weight` в одном описании, в том числе с тем же значением, — ошибка файла при загрузке. Неизвестный ключ `P` также является ошибкой файла. При отсутствии строк сохраняются значения по умолчанию из решения 84.

141. **Предел размеров шаблона.** Для `S:<width>:<height>` обе величины должны быть положительными целыми числами. Предельные габариты — 40 на 80 клеток с учётом поворота: `min(width, height) ≤ 40` и `max(width, height) ≤ 80`. Так как по решению 85 разрешены все восемь ориентаций, одинаково допустимы, например, `S:40:80` и `S:80:40`. Нулевые, отрицательные и превышающие эти пределы размеры — ошибка файла при загрузке. Это заменяет предложенный ранее, но не принятый предел 196×64. На конкретном этаже пригодность по габаритам проверяется отдельно по решениям 17 и 78а; прохождение проверки файла не гарантирует размещение на каждом этаже.

142. **Полностью прозрачная карта terrain.** Карта, в которой все клетки равны `_`, допустима; отсутствие активных клеток само по себе не является ошибкой файла. По решениям 28–29 на такой карте нельзя поместить метки монстров, предметов и входов: они требуют активную клетку. При успешном размещении такой шаблон не меняет клетки уровня, но остаётся обычным кандидатом выбора по решениям 17 и 78а и может занять попытку комнаты по решениям 75–76. Предложенное ранее требование хотя бы одной активной клетки не принято.

143. **Повтор одинакового входа.** Если в файле несколько раз указана строка `E:x:y` с одной и той же координатой, это не ошибка: повторные вхождения игнорируются. Эффективный набор входов содержит каждую координату один раз. Если в этом наборе есть хотя бы один вход, с остальным уровнем требуется соединить хотя бы один из них по решениям 3 и 12; при пустом наборе соединение не требуется.

### Рабочие решения по редактору

Ответы на вопросы 145, 147–150 и 152–153 средней и низкой критичности выбраны ассистентом по поручению пользователя. Это рабочие решения первой версии, а не ответы пользователя на отдельные вопросы. Пользователь согласовал решения 144, 144а, 146 и 151.

144. **Размещение редактора.** Редактор всегда находится в полном репозитории, содержащем исходные файлы `lib/game`.

144а. **Загрузка игровых справочников.** Редактор открывается как отдельная локальная веб-страница без запуска внешнего скрипта или сервера. При каждом запуске/сеансе пользователь одним действием выбирает папку `lib/game` через браузерный выбор каталога (например, `<input type="file" webkitdirectory>`). Редактор читает из выбранной папки `f_info.txt`, `r_info.txt`, `re_info.txt`, `k_info.txt`, `e_info.txt` и проверяет наличие всех пяти файлов; остальные файлы папки игнорирует. `a_info.txt` и `d_info.txt` для проверки отдельного шаблона комнаты в первой версии не нужны. Автоматического доступа страницы `file://` к соседним файлам нет; выбор папки повторяется в каждом новом сеансе.

145. **Создание и открытие шаблона.** Редактор позволяет создать новый шаблон, задав код, отображаемое имя и размеры, либо импортировать существующий игровой `.txt` или сохранённый редактором черновик `.json`. При создании все три карты изначально заполнены `_`.

146. **Отображение и редактирование карт.** Три слоя показываются на одной сетке с переключателем активного редактируемого слоя. Terrain остаётся видимым фоном; монстры и предметы показываются поверх него. Выбранный слой заметно выделен.

147. **Инструменты рисования.** В выбранном слое доступны кисть с протягиванием мышью, ластик, заполнение прямоугольника и выбор символа из клетки («пипетка»). Каждое действие редактирует только выбранный слой.

148. **Редактирование профилей.** Профили `T`, `M` и `I` редактируются через формы и списки, привязанные к символу соответствующего слоя. Несколько клеток могут ссылаться на один профиль. Сырой текст не является основным интерфейсом редактирования; `.txt` используется при импорте и экспорте.

149. **Редактирование входов.** Отдельный инструмент на сетке по щелчку добавляет или убирает вход `E:x:y`; рядом отображается список его координат. Инструмент допускает добавление только на активной проходимой клетке terrain по решению 29.

150. **Изменение размеров.** При изменении `S` содержимое трёх карт остаётся привязанным к верхнему левому углу, новые клетки заполняются `_`. Перед уменьшением, которое обрежет непустые клетки любого слоя или входы, редактор показывает предупреждение до применения размера.

151. **Проверка и сохранение.** Редактор показывает ошибки валидации по мере редактирования и позволяет перейти к соответствующему полю или клетке. Пользователю ясно различимы два действия: «Сохранить черновик» скачивает `.json` даже при ошибках и позволяет затем снова открыть его в редакторе; «Экспортировать `.txt` для игры» доступно только после успешной проверки всего шаблона.

152. **Отмена и сохранность работы.** Доступны Undo/Redo и предупреждение о несохранённых изменениях при закрытии страницы. Автосохранение черновика в браузере в первой версии не предусмотрено; пользователь сохраняет работу скачиванием черновика `.json` либо, после успешной проверки, игрового `.txt` по решению 151.

153. **Предпросмотр ориентаций.** Редактор показывает все восемь допустимых ориентаций в режиме просмотра: преобразуются три карты и координаты входов. Просмотр не меняет исходный шаблон.

## Состояние вопросов первой версии

**Уточнение частоты от 2026-10-14 (заменяет фиксированный флаг удвоения).** Список разрешений в `d_info.txt` принимает `I:+:<код>[:<множитель>]`; список запретов — только `I:-:<код>`. Множитель — десятичное число от 0 до 1000 включительно с точкой и максимум тремя дробными знаками, по умолчанию 1. Отрицательные, некорректные, превышающие диапазон или точность значения, повтор кода и множитель в запрете — ошибки загрузки. Значение 0 исключает шаблон из выбора, включая `ROOM_TEMPLATES_ALWAYS`, но сохраняет его базовый вес в знаменателе обычного шанса. Для исходных подходящих шаблонов с весами `w_i` задаются `W = sum(w_i)` и `S = sum(w_i * m_i)`. После двух прежних проверок необычности вероятность категории равна `min(S / (11 * W), 1)`; конкретный шаблон выбирается пропорционально `w_i * m_i`. До насыщения исходная вероятность попытки каждого шаблона умножается ровно на его множитель; вероятности других шаблонов остаются прежними. При насыщении распределение нормализуется пропорционально произведениям. Старые категории комнат делят оставшуюся вероятность с прежними относительными шансами. При отсутствии подходящих шаблонов или `S = 0` дополнительный бросок категории не выполняется. Список и множители берутся по эффективной теме этажа, в том числе для IDDC; `NO_ROOM_TEMPLATES` реального данжа имеет абсолютный приоритет. Режим `ROOM_TEMPLATES_ALWAYS` реального данжа обходит только вероятность категории и сохраняет остальные ограничения. Ограничения глубины, размера, разрушенных этажей и соединения сохраняются; неудача размещения расходует попытку без обычной комнаты взамен. Фактическое число успешных размещений не обязано умножаться на заданное число. Orc Cave использует `I:+:orc_raider_camp:2`, Mirkwood — прежнее `I:+:orc_raider_camp`. Флаг фиксированного удвоения удалён. Числа хранятся в тысячных без float; суммы и броски используют безопасную 64-битную арифметику.

Общий выбор шаблонов комнат, частота, вес категории, правило `tiny_level`, исключение разрушенных этажей, управление данжами, `P:depth`, `P:weight` и восемь ориентаций определены решениями 77а–85.

Набор полей профиля монстра первой версии закрыт решением 111: `r_idx`, `flag`, `glyph`, `level`, `only_r_idx`, `ego`; пустой профиль объявляется `M:<символ>:` по решению 110. Поля `group`, `unique` и `exclude_r_idx` отсутствуют. Происхождение удалённого `exclude_r_idx` — ранний пункт 23 и его синтаксис в пункте 92. При отсутствии `flag:UNIQUE` сохраняется стандартный шанс уникального, кроме `ego:required`/`ego:exact`, которые неявно отбирают обычных по решению 105. При `flag:UNIQUE` эго игнорируется по решению 106. При обычной замене уникального исключаются только `flag:UNIQUE` и `only_r_idx`, остальные флаги, `glyph` и `level` сохраняются по решению 107. Точный уникальный `r_idx` с обязательным/точным эго без `flag:UNIQUE` — ошибка файла по решению 108; `flag:UNIQUE` без статически подходящего уникального — ошибка по решению 109.

Набор полей профиля предмета первой версии закрыт решением 135: одиночные `tval`, `sval`, `level`, `glyph`, `quality`, `ego`, повторяемое для разных имён `flag` и пустое объявление `I:<символ>:`. Флаги берутся из `k_info.txt` и соединяются по И; `glyph` — игровой символ базового вида. Оба фильтра проверяют только базовый `k_info` до изменений, связанных с эго и артефактом, по решениям 124–131. Внутреннего `k_idx`, включающего списка, отрицательных флагов, шанса предмета и настройки стопки нет. Точный `tval`/`sval` запрещает `level`, `flag`, `glyph` по решению 126; `ego:required` допускается даже без статически совместимого эго по решению 132. Ранний предложенный артефакт проходит фильтры и предел глубины до принятия по решению 133. Для случайного вида с `ego:exact` хотя бы один статический кандидат должен быть совместим по решению 134.

Набор полей `P` закрыт решением 138: только необязательные `depth` и `weight`. Проверка значений, дубликатов и неизвестных ключей определена решениями 139–140. Активная форма всегда получает `CAVE_ROOM`, отдельного управления освещением нет по решениям 136–137. Открытых вопросов по ключам `P` первой версии не осталось.

Предел размеров `S` закрыт решением 141; полностью прозрачная terrain-карта разрешена решением 142; повторы входов определены решением 143. Рабочие решения редактора 145, 147–150 и 152–153 выбраны ассистентом по поручению пользователя. Для Q144 принято размещение редактора в полном репозитории, для Q144а — выбор папки `lib/game` пользователем в каждом сеансе для загрузки пяти справочников. Пользователь принял Q146 об одной сетке с переключением слоя и Q151 о живой проверке, сохранении черновика `.json` независимо от ошибок и экспорте игрового `.txt` только после успешной проверки. Открытых вопросов первой версии в этой спецификации не отмечено.
